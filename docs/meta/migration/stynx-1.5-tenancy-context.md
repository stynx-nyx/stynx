# Backend migration: tenancy context in STYNX 1.5

**Status:** contract for the 1.5 implementation; use only after the package release is available. This note covers backend Nest applications. The Engineer's changeset supplies the package CHANGELOG entry.

Import core and tenancy normally. Core's shared CLS middleware seeds `RequestContext` before guards, so remove application patches that reorder global interceptors or manually create a request context for tenancy. For DETRAN this means removing `patchTenantContextInterceptorOrdering`, `seedPortalPublicRequest`, `request.portalPublic`, and `portalRequestHostStorage` once the published 1.5 API replaces them.

For a public tenant endpoint, use `@PublicTenantRoute()` or `@PublicTenantRoute({ optionalAuth: true })` from `@stynx-nyx/auth`. Configure `StynxTenancyModule.forRoot({ publicTenant: { resolveHost, actorId } })` as an ordinary imported module; its providers do not become global. `resolveHost` receives the raw HTTP Host and normalized path; return an active tenant UUIDv7 or undefined. The configured tenant header and any verified token tenant claim are checked against that Host selection after UUIDv7 validation; UUID letter case does not create a conflict. Keep trusted proxy and allowed Host configuration at the deployment/application boundary. Choose a stable RFC UUID nominal actor (v4 or v7) for audit attribution; it grants no roles or permissions. Missing or invalid public options, or a marked route without the tenancy module, fail at application initialization.

Protected routes retain membership and existing header/subdomain settings. On optional-auth public tenant routes, a verified token without membership in the Host tenant is denied. If the app configures `TenantEntitlementPolicy` for `AuthContextGuard`, it also applies to the verified principal after Host selection; denial does not fall back to the nominal actor. An absent or definitively invalid token uses the nominal public actor. Custom `TokenVerifier` implementations must throw `InvalidCredentialError` from `@stynx-nyx/contracts` only for a definitive credential rejection; JWKS, configuration and unknown verifier failures must propagate. An explicit `null` verifier result remains a definitive rejection signal for compatible adapters; an undefined or non-null result without a principal fails closed. Both STYNX guards set the shared verified-public-tenant provenance marker only after successful verification; upstream request identity fields alone cannot activate an authenticated tenant branch. For `AuthContextGuard`, a direct single tenant claim (`tenant_id`, `tenantId`, `custom:tenant_id`, then `https://stynx.dev/tenant`) takes precedence; a sole `principal.tenants` entry is fallback, while a multi-tenant list alone creates no Host/claim conflict. A revoked session counts as invalid optional authentication and uses the nominal actor; protected routes still return 401. With `StynxAuthGuard`, `@ReadOnly()` on a public tenant route sets `request.stynxReadonly` for both nominal and verified requests. `AuthContextGuard` does not interpret that auth package marker, so backend-only apps must enforce read-only behavior through their own pipeline. Test both auth guards used by the application, Host/header and Host/claim mismatches, real PostgreSQL RLS, and audited writes before removing the prototype patch.
