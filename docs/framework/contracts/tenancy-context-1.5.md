# Tenancy and request context contract for STYNX 1.5

**Authority:** Architect, `INV-TENANCY-001`. **Requirements:** UPS-TEN-01…06 (all MUST under OD-S15-01). This is the implementation reference for `@stynx-nyx/core`, `contracts`, `auth`, `backend`, and `tenancy`. Existing source at 1.4.0 does not yet satisfy this contract.

## Requirements

### UPS-TEN-01 — one context before guards

`StynxCoreModule` keeps one shared `ClsModule.forRoot` dynamic descriptor across transitive imports and configures `middleware: { mount: true, setup }` on that descriptor. On Nest 11 with Express, `nestjs-cls` mounts this middleware at the adapter's route mount point, before guards and global interceptors. The `setup` initializes one active `RequestContext` for each HTTP request: a supplied valid UUIDv7 `X-Request-Id` or a generated UUIDv7, `startedAt`, and the first locale from `Accept-Language`. Invalid supplied request IDs raise `BadRequestException('X-Request-Id must be a valid UUIDv7')`. The response echoes the chosen ID in `X-Request-Id`. Repeated core imports must produce one descriptor, middleware scope, and ID. The Nest HTTP proof must force both core/tenancy `APP_INTERCEPTOR` execution orders **before `app.init()`**, when Nest 11 builds each route's interceptor chain. Swapping module imports or reordering `app.config.getGlobalInterceptors()` after initialization does not prove either served order. Spy on or wrap the actual `RequestContextInterceptor.intercept` and `TenantContextInterceptor.intercept` invocations per request and assert both observed orders, rather than checking only the configured array. For each order, a request **without** `X-Request-Id` must have the same generated ID when read by a guard before interceptors, by the handler, and in the response header, on protected and public-tenant routes. Fastify behavior is unverified in this CTG.

Guards can read this seed. After guards, the global `RequestContextInterceptor` enriches the active context using `RequestContextMutator.patch` with only trusted `request.tenantId`, `request.principal`/`actor`/`user`, and verified `request.stynxClaims`: `tenantId`, `actorId`, and `sessionId` where present. This works for auth-only apps without tenancy, including apps using only backend `AuthContextGuard`: its verified principal and resolved tenant populate post-guard `actorId` and `tenantId`. A string `Principal.claims.sid` on the principal produced by a successful `AuthContextGuard` verification is also a trusted session source, so the guard exposes it as a request-local verified session value (for example `request.verifiedSessionId`) and core patches `RequestContext.sessionId` from that value when present. The same rule applies to a verified optional-auth public tenant request; an absent `sid` leaves `sessionId` unset. Core must not infer session identity from arbitrary `request.principal.claims` or parsed, unverified bearer claims, and invalid or absent optional credentials expose no verified session value. `TenantContextInterceptor` also patches the existing context after resolution; its ordering against the core interceptor does not matter. Direct consumers of the exported `RequestContextInterceptor` retain its ability to initialize a context if one is absent, but it must never reopen an already active context. The pre-guard seed is not a license to trust request headers as identity.

### UPS-TEN-02 and 03 — public tenant route

The legacy plain `@Public()` route retains `PermissionGuard`'s existing public
bypass, even if it also has `@Permission`. Only the distinct public-tenant
marker changes this behavior. On entry to an optional-auth public tenant
route, each guard clears prior request-local identity and verification fields
before evaluating the token. An absent or invalid bearer cannot retain a
principal, actor, user, tenant, session, claim, or entitlement callback left by
upstream middleware.

`@stynx-nyx/contracts` exports a runtime `InvalidCredentialError` for a definitive credential rejection. Both built-in verification paths (`StynxJwtValidator` and `CognitoTokenVerifier`) and custom `TokenVerifier` implementations use that type only for malformed tokens, bad signatures, expired or not-yet-valid tokens, and failed issuer, audience, or token-use checks. An absent or malformed bearer header can be classified locally before verification. The optional-auth guard catches only `InvalidCredentialError` and then proceeds with the nominal actor; it never treats an arbitrary `Error`, a non-null result missing its principal, or an unknown JOSE error as invalid credentials. For compatibility with existing `TokenVerifier` adapters, an explicit `null` result is a definitive credential-rejection signal on the optional route; `undefined` or a malformed non-null result fails closed. JWKS fetch/refresh, key-source configuration, and other verifier failures propagate and fail the request. A verifier must preserve that distinction when wrapping third-party errors; an ambiguous failure propagates. Protected routes retain their existing denial behavior. A verified token whose session lookup definitively returns no active session may use the nominal actor on this optional route; a thrown session lookup error propagates.

For `StynxJwtValidator`, a JWKS response from `SessionJwtSigningService.getJwks()` or `jwksUri` with missing `keys`, a non-array `keys`, an empty array, or no usable verification key is a key-source/configuration failure. It must throw a non-`InvalidCredentialError` and must never turn a valid optional bearer into the nominal actor. This follows the existing `resolveKeys`/`verify` architecture: validate the fetched/cached key set before mapping over keys; a zero-key map cannot establish a bad signature. A token malformed independently of the key source may still be an invalid credential.

When at least one usable key is present but **all keys reject the signature**, the cached set may be stale after rotation. For both the signing-service and `jwksUri` paths, force one fresh key-set resolution that bypasses the normal 12-hour cache, then retry verification once. Do not refresh for a claim failure after a valid signature (issuer, audience, expiry or not-before). A successful refresh that yields a usable set whose keys all reject the signature permits `InvalidCredentialError`; a refresh failure, missing/empty/malformed set, or unusable keys propagates as a non-`InvalidCredentialError`. Refreshes are bounded to one per verification attempt and coalesced per key source. Limit forced refresh starts to at most one per source in a 30-second window; when a miss occurs while refresh is suppressed and no newly refreshed set can establish definitive rejection, fail the request with a non-`InvalidCredentialError` rather than downgrading to the nominal actor. A valid token signed by a newly published key must authenticate after the allowed refresh; neither a stale cached set nor a refresh outage may be labeled a definitive bad credential. This applies to `jwksUri` even when no `SessionJwtSigningService` is registered.

`@stynx-nyx/contracts` also exports one shared request-local provenance symbol, `STYNX_VERIFIED_PUBLIC_TENANT_PRINCIPAL`. Both `StynxAuthGuard` and `AuthContextGuard` delete it and clear identity fields on entry to a public-tenant route, then set it **only** after successful token verification and any applicable session check. A non-optional public-tenant route, absent/invalid credential, and revoked session leave it unset. `TenantContextInterceptor` accepts `request.stynxClaims`, `request.principal`, `verifiedTenantClaim`, verified session ID, and the entitlement callback as authenticated inputs only when that symbol is set; without it, tenancy uses the nominal actor and ignores all upstream identity fields. This marker is distinct from the auth package's private verified-grant marker used by `PermissionGuard`; backend `AuthContextGuard` must not create a grant for that auth-specific permission guard. The marker carries provenance, not a tenant decision: Host selection and membership remain mandatory.

For a verified `AuthContextGuard` principal, the single tenant claim compared with Host is the first non-empty string in this order: `principal.claims.tenant_id`, `tenantId`, `custom:tenant_id`, `https://stynx.dev/tenant`. If none exists, use `principal.tenants` only when it contains exactly one distinct tenant. A multi-tenant list alone supplies no single claim for Host conflict detection; the actor still needs active membership in the Host tenant. A direct claim takes precedence over the list, and a direct claim for B under Host A raises `TENANCY:CONFLICT:host-claim` even if the list also contains A. Compare UUID spelling without letter-case differences as specified below. This definition covers the Cognito-shaped claims read by `CognitoTokenVerifier` while leaving Host as the sole selector.

`@stynx-nyx/auth` exports `@PublicTenantRoute()` and `@PublicTenantRoute({ optionalAuth: true })`. The decorator composes `STYNX_PUBLIC_ROUTE` with a distinct `STYNX_PUBLIC_TENANT_ROUTE` metadata key exported from `@stynx-nyx/contracts`; its route may be explicitly public under `INV-RBAC-001`. Both `StynxAuthGuard` and `AuthContextGuard` inspect the distinct metadata **before** any generic public early return. `scripts/list-routes.mjs` and `scripts/verify-api-coverage.mjs` must recognize the marker as explicit public route metadata. All other unbound routes remain deny-default. On a public tenant route that also declares a permission (`@Permission(...)`, the current auth-package spelling of the requested `@RequirePermission` behavior), `PermissionGuard` must evaluate the permission despite the composed `STYNX_PUBLIC_ROUTE` marker. It reads only permissions on a principal established by `StynxAuthGuard` from a verified token; a nominal actor, absent principal, or principal without verified-token provenance has zero permissions and is denied with the existing `ForbiddenException('Missing permission <key>')`. Register `StynxAuthGuard` before `PermissionGuard` on that route so the latter consumes trusted guard output; if the order is wrong or the trusted principal is absent, permission evaluation fails closed. Tenancy still enforces Host selection and active membership after guards. With no permission marker, the public tenant route remains public and the nominal actor can reach its handler.

`StynxTenancyModule.forRoot({ publicTenant: { resolveHost, actorId } })` owns the options. `resolveHost({ host, path })` returns a tenant UUIDv7 or undefined, synchronously or asynchronously. `host` is the raw HTTP `Host` header (`request.headers.host`), never an implicitly trusted `X-Forwarded-Host` or proxy-rewritten `request.hostname`; `path` is the normalized request path. Host alone selects the public tenant. `StynxTenancyModule.forRoot` remains an ordinary imported dynamic module, not `global: true`; its existing exports remain available through explicit module imports. Bootstrap checks may use `ModuleRef.get(..., { strict: false })` to find the options token without making all tenancy providers global. `headerName` (default `X-Tenant-Id`) continues to configure the comparison header. Header and verified token tenant claims can only corroborate or conflict with the Host result; neither selects another tenant. Keep the existing UUIDv7 validation and compare tenant UUID strings after ASCII lower-case normalization, so letter case alone never creates a conflict. This changes neither tenant selection nor the established 400 for a malformed or non-v7 selected tenant ID. A Host A/header B mismatch is 400 `TENANCY:CONFLICT:host-header`; a Host A/verified claim B mismatch is 400 `TENANCY:CONFLICT:host-claim`. These checks occur before domain access. A missing or unresolved Host tenant uses the existing 400 missing-tenant exception and body. A resolved tenant must be active (`is_active = true`, state active); public selection does not require a membership row. Inactive, suspended, archived, or purged tenants cannot enter a public context.

`actorId` is a required RFC UUID, with v4 and v7 accepted. Missing `publicTenant`, missing `resolveHost` or `actorId`, or invalid `actorId` fails module initialization. A route with `@PublicTenantRoute` requires the tenancy module and valid options; the app fails initialization with a clear error when absent, before it serves requests. The public-tenancy options injection token `STYNX_PUBLIC_TENANT_OPTIONS` is exported from `contracts` and provided by tenancy. Bootstrap checks in `@stynx-nyx/auth`'s `StynxAuthModule` and `@stynx-nyx/backend`'s `StynxAuthModule` inspect discovered controller and handler metadata and require that token; the latter covers apps using only `AuthContextGuard`. Both fail with a clear missing-tenancy-module error before serving requests. These checks use existing package dependencies (`auth` and `backend` already depend on `contracts`) and do not require a new dependency edge. PostgreSQL audit, flow, and worklist SQL cast `app.actor_id` to `uuid`; a non-UUID nominal actor would fail an audited write despite a valid HTTP response.

For an anonymous public request, tenancy sets `request.tenantId` and patches `RequestContext.tenantId` and `.actorId` with the active Host tenant and nominal actor. The nominal actor has no inherited roles or permissions; a forged, unsigned, or invalid token cannot set actor, tenant, session, roles, or permissions. With `optionalAuth: true`, a valid bearer follows the complete authenticated flow. Its verified actor must have active membership in the Host tenant; absence yields 403 `TENANT_ACCESS_DENIED` with no downgrade to the nominal actor. When `AuthContextGuard` has a configured `TenantEntitlementPolicy`, it attaches a trusted request-local entitlement callback bound to its verified principal; the guard must not call the policy with a header or guessed tenant. After Host selection and active-tenant and membership checks, `TenantContextInterceptor` invokes that callback with the selected Host tenant before patching context or entering the handler. The callback calls `isEntitled({ principal, tenantId: hostTenant })`; a false result or a thrown policy error fails closed and cannot select another tenant or fall back to the nominal actor. This handoff uses the existing guard-to-interceptor request path and introduces no package dependency. A policy denial retains the protected flow's `ForbiddenException('Principal is not entitled for tenant context')` response and never downgrades to the nominal actor. Invalid or absent bearer follows the public flow, without 401 or 403 merely for its token state. A token whose session was revoked is invalid for optional authentication: `StynxAuthGuard` clears or avoids all verified identity fields and uses the nominal public actor, whereas a protected route retains its existing 401 `STYNX session is no longer active`. Session lookup or verifier infrastructure failures are not silently treated as revoked or invalid credentials, under the typed-error distinction above. Without `optionalAuth`, the route remains public and token claims do not become authority. Plain `@Public()` routes and their legacy unverified-claim fallback are outside this CTG; preserve their existing semantics without widening trust.

`AuthContextGuard` retains its verified principal but defers tenant choice on a public tenant route to tenancy. Its hard-coded `x-tenant-id` resolver must not override `resolveHost` or the configured comparison header there. Protected routes retain its existing resolver and entitlement behavior. `StynxAuthGuard` likewise checks the public-tenant marker before its generic `STYNX_PUBLIC_ROUTE` return. Both guards must make valid and invalid optional-token branches distinguishable to tenancy without treating raw bearer text as verified claims. Combining `@ReadOnly()` and `@PublicTenantRoute` keeps the auth package's existing read-only marker semantics: `StynxAuthGuard` sets `request.stynxReadonly = true` on both nominal and verified branches before the handler, including optional authentication. `@ReadOnly()` does not grant permissions or bypass Host selection, membership, or entitlement. `AuthContextGuard` has never consumed the auth package's read-only metadata; backend-only adopters must enforce a read-only policy in their own pipeline rather than assume this marker affects that guard.

### UPS-TEN-04 — resolver context

`TenantResolverContext` in `contracts` adds optional `host?: string` and `path?: string`. Guards supply these from the raw Host header and normalized path to consumer resolvers where applicable. Existing resolvers accepting only `headerTenantId` and `principal` remain source-compatible.

### UPS-TEN-05 — protected compatibility and negative cases

Existing protected routes keep `isOptionalTenancyPath`, configurable `headerName`, `allowSubdomain`, membership cache, UUIDv7 tenant validation, and current messages. Header/claim disagreement, actor absent, and missing or inactive membership continue to fail closed with 403 `TENANT_ACCESS_DENIED`. A tenant UUID that is not v7 remains 400. A principal with membership only in A cannot select B. Public requests under A cannot read B's rows under real PostgreSQL RLS. Request context and audited writes must work for nominal UUID actors under A's RLS.

The exact runtime errors under the current `StynxErrorFilter` are:

| Case                 | Exception                          | HTTP | JSON body without `STYNX_ERROR_TRANSLATOR`                                                                                                             |
| -------------------- | ---------------------------------- | ---: | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Missing tenant       | `BadRequestException`              |  400 | `{"message":"Tenant context is required: provide X-Tenant-Id, a tenant bearer claim, or a matching subdomain","error":"Bad Request","statusCode":400}` |
| Membership denied    | `ForbiddenException`               |  403 | `{"message":"TENANT_ACCESS_DENIED","error":"Forbidden","statusCode":403}`                                                                              |
| Host/header conflict | **`@stynx-nyx/core`** `StynxError` |  400 | `{"code":"TENANCY:CONFLICT:host-header","message":"Tenant source conflict: Host and X-Tenant-Id disagree"}`                                            |
| Host/claim conflict  | **`@stynx-nyx/core`** `StynxError` |  400 | `{"code":"TENANCY:CONFLICT:host-claim","message":"Tenant source conflict: Host and authenticated claim disagree"}`                                     |

The configured header name replaces `X-Tenant-Id` in the first and third messages. Tenancy raises both conflict errors with `{ status: 400, code }` and no `context`. Do not use the homonymous `contracts` `StynxError`, which lacks `status` and is not caught by the core filter. The filter passes `HttpException.getResponse()` through and serializes core `StynxError` as `{code,message,context?}`. With a registered translator and active locale, conflict `message` may be localized by `messageKey`; status and code remain fixed. No error schema change is authorized by this CTG.

### UPS-TEN-06 — migration

Consumers that manually reorder global interceptors or seed portal public requests should remove the DETRAN prototype `patchTenantContextInterceptorOrdering`, `seedPortalPublicRequest`, `request.portalPublic`, and `portalRequestHostStorage` after adopting the released middleware and `@PublicTenantRoute` API. Replace the patch with `StynxTenancyModule.forRoot({ publicTenant: { resolveHost, actorId } })`; retain a Host allow-list at the application boundary, and configure proxy Host forwarding explicitly in deployment. See [the backend migration note](../../meta/migration/stynx-1.5-tenancy-context.md). The Engineer's package changeset supplies the package CHANGELOG entry.

## Verification boundary

Inspector sensors should exercise both module/interceptor registration orders, multiple core imports, pre-guard context, direct interceptor use, auth-only and backend-only applications with verified `Principal.claims.sid` propagation, both auth guards, typed invalid-credential and JWKS/configuration/unknown-error branches, shared provenance clearing and setting, Cognito-shaped claim precedence, bootstrap errors, exact HTTP bodies, configured headers and case-insensitive UUID equality, entitlement allow/deny, revoked sessions, `@ReadOnly` combinations, nominal denial and verified grant for a public tenant route with `@Permission`, public and protected token branches, and active/inactive tenants. Use real PostgreSQL for two-tenant RLS and nominal-actor audited writes; run the existing RLS negative and smoke checks. The later CTG-2 contract must pin SSE-06's filter callback independently of AUTHZ-07 until CTG-3 lands.

Minimum review sensors for this contract:

- **Nest HTTP order:** force the two global interceptor orders before `app.init()`, spy on real per-request interceptor calls for protected and public-tenant routes, and match the generated UUIDv7 observed by the pre-interceptor guard, handler and response when no request ID is supplied.
- **STYNX JWKS:** use a real usable RSA JWK with a bad-signature token to prove the typed invalid path. Missing, non-array, empty and unusable key sets from each source must reject as non-`InvalidCredentialError`; an optional HTTP route must fail rather than return 200 nominal. With a stale cached set, a rotated valid token must succeed after one fresh signing-service or `jwksUri` resolution. Refresh rejection or a rate-limited refresh must fail without nominal fallback. Assert one refresh per attempt and the 30-second source limit with controlled time and concurrent misses.
- **Backend/JOSE HTTP:** make `AuthContextGuard` receive an `InvalidCredentialError` for a present bearer and show 200 nominal with no principal, then a generic/JWKS error and show failure. For `CognitoTokenVerifier`, test definitive JOSE codes (expired, bad signature, claim validation) as typed invalid and `ERR_JWKS_TIMEOUT`, `ERR_JWKS_NO_MATCHING_KEY`, and fetch failures as propagated errors.
- **Session and provenance:** over HTTP, a revoked optional STYNX session returns the nominal actor and Host tenant without principal or session ID. Unit sensors must show the shared provenance symbol unset. Pre-seed all identity/session/entitlement fields and both the shared provenance and auth-private grant markers; absent bearer, typed-invalid bearer and non-optional public-tenant route must clear them in both guards as applicable. An unmarked upstream tenant-B claim under Host A must neither trigger a Host/claim conflict nor authenticate the actor. A backend-only `AuthContextGuard` principal, even with a matching permission, cannot satisfy the auth package's `PermissionGuard` verified-grant requirement.
