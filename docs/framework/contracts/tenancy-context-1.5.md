# Tenancy and request context contract for STYNX 1.5

**Authority:** Architect, `INV-TENANCY-001`. **Requirements:** UPS-TEN-01…06 (all MUST under OD-S15-01). This is the implementation reference for `@stynx-nyx/core`, `contracts`, `auth`, `backend`, and `tenancy`. Existing source at 1.4.0 does not yet satisfy this contract.

## Requirements

### UPS-TEN-01 — one context before guards

`StynxCoreModule` keeps one shared `ClsModule.forRoot` dynamic descriptor across transitive imports and configures `middleware: { mount: true, setup }` on that descriptor. On Nest 11 with Express, `nestjs-cls` mounts this middleware at the adapter's route mount point, before guards and global interceptors. The `setup` initializes one active `RequestContext` for each HTTP request: a supplied valid UUIDv7 `X-Request-Id` or a generated UUIDv7, `startedAt`, and the first locale from `Accept-Language`. Invalid supplied request IDs raise `BadRequestException('X-Request-Id must be a valid UUIDv7')`. The response echoes the chosen ID in `X-Request-Id`. Repeated core imports must produce one descriptor, middleware scope, and ID. Fastify behavior is unverified in this CTG.

Guards can read this seed. After guards, the global `RequestContextInterceptor` enriches the active context using `RequestContextMutator.patch` with only trusted `request.tenantId`, `request.principal`/`actor`/`user`, and verified `request.stynxClaims`: `tenantId`, `actorId`, and `sessionId` where present. This works for auth-only apps without tenancy. It must not use parsed, unverified bearer claims on the new public tenant path. `TenantContextInterceptor` also patches the existing context after resolution; its ordering against the core interceptor does not matter. Direct consumers of the exported `RequestContextInterceptor` retain its ability to initialize a context if one is absent, but it must never reopen an already active context. The pre-guard seed is not a license to trust request headers as identity.

### UPS-TEN-02 and 03 — public tenant route

`@stynx-nyx/auth` exports `@PublicTenantRoute()` and `@PublicTenantRoute({ optionalAuth: true })`. The decorator composes `STYNX_PUBLIC_ROUTE` with a distinct `STYNX_PUBLIC_TENANT_ROUTE` metadata key exported from `@stynx-nyx/contracts`; its route may be explicitly public under `INV-RBAC-001`. Both `StynxAuthGuard` and `AuthContextGuard` inspect the distinct metadata **before** any generic public early return. `scripts/list-routes.mjs` and `scripts/verify-api-coverage.mjs` must recognize the marker as explicit public route metadata. All other unbound routes remain deny-default.

`StynxTenancyModule.forRoot({ publicTenant: { resolveHost, actorId } })` owns the options. `resolveHost({ host, path })` returns a tenant UUIDv7 or undefined, synchronously or asynchronously. `host` is the raw HTTP `Host` header (`request.headers.host`), never an implicitly trusted `X-Forwarded-Host` or proxy-rewritten `request.hostname`; `path` is the normalized request path. Host alone selects the public tenant. `headerName` (default `X-Tenant-Id`) continues to configure the comparison header. Header and verified token tenant claims can only corroborate or conflict with the Host result; neither selects another tenant. A Host A/header B mismatch is 400 `TENANCY:CONFLICT:host-header`; a Host A/verified claim B mismatch is 400 `TENANCY:CONFLICT:host-claim`. These checks occur before domain access. A missing or unresolved Host tenant uses the existing 400 missing-tenant exception and body. A resolved tenant must be active (`is_active = true`, state active); public selection does not require a membership row. Inactive, suspended, archived, or purged tenants cannot enter a public context.

`actorId` is a required RFC UUID, with v4 and v7 accepted. Missing `publicTenant`, missing `resolveHost` or `actorId`, or invalid `actorId` fails module initialization. A route with `@PublicTenantRoute` requires the tenancy module and valid options; the app fails initialization with a clear error when absent, before it serves requests. The public-tenancy options injection token `STYNX_PUBLIC_TENANT_OPTIONS` is exported from `contracts` and provided by tenancy. Bootstrap checks in `@stynx-nyx/auth`'s `StynxAuthModule` and `@stynx-nyx/backend`'s `StynxAuthModule` inspect discovered controller and handler metadata and require that token; the latter covers apps using only `AuthContextGuard`. Both fail with a clear missing-tenancy-module error before serving requests. These checks use existing package dependencies (`auth` and `backend` already depend on `contracts`) and do not require a new dependency edge. PostgreSQL audit, flow, and worklist SQL cast `app.actor_id` to `uuid`; a non-UUID nominal actor would fail an audited write despite a valid HTTP response.

For an anonymous public request, tenancy sets `request.tenantId` and patches `RequestContext.tenantId` and `.actorId` with the active Host tenant and nominal actor. The nominal actor has no inherited roles or permissions; a forged, unsigned, or invalid token cannot set actor, tenant, session, roles, or permissions. With `optionalAuth: true`, a valid bearer follows the complete authenticated flow. Its verified actor must have active membership in the Host tenant; absence yields 403 `TENANT_ACCESS_DENIED` with no downgrade to the nominal actor. Invalid or absent bearer follows the public flow, without 401 or 403 merely for its token state. Without `optionalAuth`, the route remains public and token claims do not become authority. Plain `@Public()` routes and their legacy unverified-claim fallback are outside this CTG; preserve their existing semantics without widening trust.

`AuthContextGuard` retains its verified principal but defers tenant choice on a public tenant route to tenancy. Its hard-coded `x-tenant-id` resolver must not override `resolveHost` or the configured comparison header there. Protected routes retain its existing resolver and entitlement behavior. `StynxAuthGuard` likewise checks the public-tenant marker before its generic `STYNX_PUBLIC_ROUTE` return. Both guards must make valid and invalid optional-token branches distinguishable to tenancy without treating raw bearer text as verified claims.

### UPS-TEN-04 — resolver context

`TenantResolverContext` in `contracts` adds optional `host?: string` and `path?: string`. Guards supply these from the raw Host header and normalized path to consumer resolvers where applicable. Existing resolvers accepting only `headerTenantId` and `principal` remain source-compatible.

### UPS-TEN-05 — protected compatibility and negative cases

Existing protected routes keep `isOptionalTenancyPath`, configurable `headerName`, `allowSubdomain`, membership cache, UUIDv7 tenant validation, and current messages. Header/claim disagreement, actor absent, and missing or inactive membership continue to fail closed with 403 `TENANT_ACCESS_DENIED`. A tenant UUID that is not v7 remains 400. A principal with membership only in A cannot select B. Public requests under A cannot read B's rows under real PostgreSQL RLS. Request context and audited writes must work for nominal UUID actors under A's RLS.

The exact runtime errors under the current `StynxErrorFilter` are:

| Case                 | Exception                          | HTTP | JSON body without `STYNX_ERROR_TRANSLATOR`                                                                                                             |
| -------------------- | ---------------------------------- | ---: | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Missing tenant       | `BadRequestException`              |  400 | `{"message":"Tenant context is required: provide X-Tenant-Id, a tenant bearer claim, or a matching subdomain","error":"Bad Request","statusCode":400}` |
| Membership denied    | `ForbiddenException`               |  403 | `{"message":"TENANT_ACCESS_DENIED","error":"Forbidden","statusCode":403}`                                                                              |
| Host/header conflict | **`@stynx-nyx/core`** `StynxError` |  400 | `{"code":"TENANCY:CONFLICT:host-header","message":"Tenant source conflict: Host and X-Tenant-Id disagree"}`                                            |
| Host/claim conflict  | **`@stynx-nyx/core`** `StynxError` |  400 | `{"code":"TENANCY:CONFLICT:host-claim","message":"Tenant source conflict: Host and authenticated claim disagree"}`                                     |

The configured header name replaces `X-Tenant-Id` in the first and third messages. Tenancy raises both conflict errors with `{ status: 400, code }` and no `context`. Do not use the homonymous `contracts` `StynxError`, which lacks `status` and is not caught by the core filter. The filter passes `HttpException.getResponse()` through and serializes core `StynxError` as `{code,message,context?}`. With a registered translator and active locale, conflict `message` may be localized by `messageKey`; status and code remain fixed. No error schema change is authorized by this CTG.

### UPS-TEN-06 — migration

Consumers that manually reorder global interceptors or seed portal public requests should remove the DETRAN prototype `patchTenantContextInterceptorOrdering`, `seedPortalPublicRequest`, `request.portalPublic`, and `portalRequestHostStorage` after adopting the released middleware and `@PublicTenantRoute` API. Replace the patch with `StynxTenancyModule.forRoot({ publicTenant: { resolveHost, actorId } })`; retain a Host allow-list at the application boundary, and configure proxy Host forwarding explicitly in deployment. See [the backend migration note](../../meta/migration/stynx-1.5-tenancy-context.md). The Engineer's package changeset supplies the package CHANGELOG entry.

## Verification boundary

Inspector sensors should exercise both module/interceptor registration orders, multiple core imports, pre-guard context, direct interceptor use, auth-only applications, both auth guards, bootstrap errors, exact HTTP bodies, configured headers, public and protected token branches, and active/inactive tenants. Use real PostgreSQL for two-tenant RLS and nominal-actor audited writes; run the existing RLS negative and smoke checks. The later CTG-2 contract must pin SSE-06's filter callback independently of AUTHZ-07 until CTG-3 lands.
