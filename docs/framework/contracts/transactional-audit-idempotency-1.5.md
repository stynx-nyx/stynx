# Transactional audit and idempotency — STYNX 1.5

**Authority:** Architect. **Group:** CTG-0005/R-0002. **Source:** DETRAN C-0002 §6.2, UPS-TXN-01…05 (all MUST under OD-S15-01). This is an opt-in command mode. Unmarked routes retain published behavior.

## CTG9 composition with append and audit epochs

The CTG5 envelope still writes audit and idempotency **after** its handler callback. A generic `OutboxService.appendInTransaction(trx,event)` inside that callback may therefore leave the transaction writable; its append first takes the tenant audit-chain advisory and then the outbox tenant-clock row, retaining both to commit. The envelope's later audit writer reuses that chain key, preserving the chain→clock order, and the command response remains atomic with the event. A long callback after append holds the clock and can make same-tenant SSE `now()` return the existing source-unavailable 503 after a bounded `lock_timeout`; clients retry. OFS uses a distinct strict `Database.txIndependent` item boundary and seals its terminal append with `SET LOCAL transaction_read_only = on`, after domain, consumption, receipt and audit writes. The item must not be run as a nested savepoint inside the CTG5 envelope. This additive rule does not change legacy CTG5 behavior when no append is used.

`Database.txIndependent` uses a mutable AsyncLocalStorage holder `{held,strict}` that survives derived request/system contexts. In strict mode, `Database.tx` fails with `IndependentTransactionConnectionError` **before** `pool.connect` if it would acquire a second connection, even if CLS lost `TX_CONTEXT_KEY`; the effect and audit port must use the received `Transaction`. The holder is cleared in `finally` after commit/rollback. Outside strict mode, published nested/savepoint and derived-context `Database.tx` behavior remains. Top-level `TxOptions.isolation` is applied before the first session query; a nested mismatch fails. Outbox/audit writers validate READ COMMITTED on the live connection. The three audit writers reject RR/SERIALIZABLE before head selection with SQLSTATE `40001`, MESSAGE `audit_chain_requires_read_committed`; data maps precisely this error to nonretryable `AuditChainIsolationError`, while genuine 40001/40P01 remain retryable at the outer boundary. Subsequent writes after an OFS seal yield SQLSTATE `25006` → `ReadOnlyViolationError`.

Migration ≥0021 makes `audit.fn_row_change`, `audit.write` and `audit.write_command_event` take the same advisory key before head selection and assign an explicit monotonically increasing `occurred_at` under READ COMMITTED. `audit.ensure_monthly_partition` receives that **chosen** timestamp before hash/insert, including at a month boundary. Owner `AuditSqlSink` may write a real tenant; `audit.write` remains revoked to app. The first chain key in a transaction is recorded in local `stynx.audit_chain_key`; X→NULL or another key raises `STY41` → `AuditChainKeyMismatchError` before another advisory. This GUC is self-protection, not a SQL privilege boundary. Legacy segments are classified and sealed into new epochs without rehashing; `audit.verify_chain` partitions by epoch and `audit.verify_current_epoch` starts at the new anchor. The Engineer's changeset and migration guide must disclose that `TxOptions.isolation` becomes effective and an audited RR/SERIALIZABLE write now fails with typed `AuditChainIsolationError`. See [ADR-OUTBOX-0002](../../../law/adr/ADR-OUTBOX-0002-event-log-and-delivery.md) and the [CTG9 OBX contract](../../../work/rounds/R-0002/ctg9-obx-contract.md).

## Public surface and one boundary

`@TransactionalCommand(options?: TransactionalCommandOptions)`, `StynxTransactionalCommandModule.forRoot(options: StynxTransactionalCommandModuleOptions)` and `TransactionalCommandInterceptor` are exported from `@stynx-nyx/backend`. Module options expose `auditSink: TransactionalAuditSink` and optional command defaults for `scope`, `mismatchCode`, `persistStatus` and `lockTimeoutMs`; `Database` and `TransactionalIdempotencyStore` are injected from their packages. Route options override module defaults. The module installs one global boundary with `APP_INTERCEPTOR`. A marked route also requires `@Idempotent({ transactional: true, ... })` from `@stynx-nyx/idempotency` and `@Audit({ ..., transactional: true })` from `@stynx-nyx/backend`. Existing positional `@Idempotent(headerName?, ttlMs?)` calls remain valid; the new object overload is additive. `AuditMetadata.transactional?: boolean` is additive. The boundary rejects incomplete or conflicting markings before `next.handle()`. The legacy audit/idempotency interceptors defer transactional routes to this boundary, regardless of global or method interceptor registration order. A marked route without the command module fails closed at request entry, not through a legacy interceptor. The module's Database, transactional sink and key store providers must resolve at boot; missing compatible providers fail at boot.

`TransactionalCommandOptions` contains `scope?: (ctx: TransactionalCommandContext) => string`, `mismatchCode?: string`, `persistStatus?: (outcome: TransactionalCommandOutcome) => boolean`, and `lockTimeoutMs?: number`. The context exposes trusted tenant/actor IDs, method, concrete path, request and raw parsed body. Default scope is trusted `RequestContext.actorId`, never a request header. A public route deliberately selects `scope: () => 'public'` and still supplies a configured nominal or verified actor for `requireActor`. Missing/empty scope, trusted tenant/actor or supplied key rejects before handler execution. Default mismatch code is `IDEMPOTENCY:CONFLICT:duplicate-key`; a configured code must match `law/schemas/error-envelope.schema.json` and is checked at bootstrap; default status policy selects 2xx; default lock timeout is 5,000 ms. Invalid callback output fails closed.

**Actor provenance and execution type:** `TransactionalCommandInterceptor` accepts only Nest HTTP execution contexts; a job handler that does not serve HTTP uses `Database.tx` under CTG4's persisted actor context and does not invoke this decorator/interceptor. `RequestContext.actorId` is the selected actor value, not proof that a guard verified it. A marked protected HTTP command requires a built-in STYNX auth guard on the served route, the guard-owned `STYNX_VERIFIED_TENANT_ID`, `request.principal.id` (which both built-in guards set), and equality of those tenant/actor values with the active `RequestContext`. If `request.stynxClaims` is present, its `sub` and `tenantId` must also equal `principal.id` and the verified tenant marker; any disagreement rejects before the command transaction or handler. `AuthContextGuard` clears pre-existing `stynxClaims` at request entry before successful verification, while `StynxAuthGuard` replaces them on successful verification. A later consumer guard mutating principal or claims is outside the request-origin threat boundary; the equality check still detects a mismatch, but these in-process signals are not cryptographic protection against malicious application code. Other authentication guards have no CTG5 command provenance contract.

A public HTTP command must be marked `@PublicTenantRoute`; plain `@Public()` and `@System()` supply no command provenance. `@stynx-nyx/contracts` adds `STYNX_RESOLVED_TENANT_COMMAND_CONTEXT`, a DI token for `ResolvedTenantCommandContextPort` whose **only** public method, including on its prototype, is `get(request): { tenantId: string; actorId: string; mode: 'protected' | 'nominal' | 'verified' } | undefined`. `StynxTenancyModule` exports the provider. The provider's read closure observes a module-private `WeakMap` keyed by the request; the write function stays module scoped, is unreachable through the provider object/prototype, and is not exported by the package. `TenantContextInterceptor` writes exactly once on its success path, after Host/active-tenant/membership/optional-entitlement validation and after its `RequestContext` patch, immediately before `next.handle()`. It writes no entry on an error path or for an optional path it does not resolve. On a protected route, the interceptor retains the exact actor ID passed to its existing `hasActiveMembership(actorId, tenantId)` check (an internal return-value change, not a public API change). It writes `mode:'protected'` only when that checked actor equals both the patched `RequestContext.actorId` and `request.principal.id`, and the checked tenant equals the patched `RequestContext.tenantId` and `STYNX_VERIFIED_TENANT_ID`. On any mismatch it writes no port entry, so the command boundary rejects before opening a transaction or running handler SQL. This comparison does not change the existing membership lookup or non-command route behavior. On a public route, `mode:'nominal'` uses the configured UUID `publicTenant.actorId`; `mode:'verified'` requires the existing `STYNX_VERIFIED_PUBLIC_TENANT_PRINCIPAL` marker, a built-in guard invocation, active membership, and optional entitlement; its recorded `actorId` must equal `request.principal.id`, and any present `stynxClaims.sub` and `.tenantId` must equal that principal ID and the Host-selected tenant. A mismatch writes no port entry and rejects before command SQL. Both public modes record the Host-selected tenant. The command boundary requires the mode appropriate to route metadata and exact equality among port result, active `RequestContext` and verified guard identity where applicable. A pre-seeded request property/symbol or nonempty context cannot create a port result.

`StynxTransactionalCommandModule` validates guard/provider wiring at `onApplicationBootstrap` through route/class `@UseGuards` metadata and Nest `APP_GUARD` providers. Imperative `app.useGlobalGuards(...)` registrations, including those made before `app.init()`, are unsupported command provenance because Nest 11 does not expose that registry through a public DI interface; a command relying only on such a guard fails the boot check. A protected command and an `@PublicTenantRoute({ optionalAuth: true })` command require `StynxAuthGuard` or `AuthContextGuard` on their route/class or as a global guard. An anonymous-only `@PublicTenantRoute()` command needs no auth guard but still needs the tenancy port. Guard identification uses a new `@stynx-nyx/contracts` symbol brand defined as an **own property** of each built-in guard constructor and checked with `Object.hasOwn` and value `=== true` on the concrete Nest guard metatype or instance constructor in route/class metadata or `APP_GUARD` providers. A matching class name or a subclass inheriting the static brand is insufficient. Because the brand symbol is public, a consumer can deliberately self-brand a guard; this is inside the in-process trusted-code boundary, not a defense against malicious application code. The brand adds a narrow `packages/auth` edit for `StynxAuthGuard`, while backend owns its `AuthContextGuard` edit; it creates no backend→auth dependency. Every guard executes before interceptors, so no relative APP_GUARD ordering requirement is added by CTG5. The existing tenancy boot check continues to reject `@PublicTenantRoute` without configured `publicTenant`; CTG5 additionally requires the exported port provider on marked public commands and on protected commands when tenancy is installed.

The command interceptor must execute **inside** the core/tenancy context interceptors, after their tenant/actor patch, and before the handler. Its ordering independence applies to legacy audit/idempotency participants, not to identity establishment. When tenancy is installed, a protected or public command requires the tenancy port result before opening or reusing any transaction; the core → command → tenancy order therefore fails before command SQL or handler. An auth-only app without tenancy uses the built-in guard marker, principal and active `RequestContext` equality; absent core context enrichment fails before command SQL. Immediately after opening or reusing the app-role transaction and before subscribing to `next.handle()`, the boundary verifies the live connection's `current_user`, `app.role`, `app.tenant_id`, and `app.actor_id` against the selected role/tenant/actor. `Database.tx({ requireActor:true })` performs the same nested identity check before a savepoint or caller SQL. A mismatch rolls back and never enters the handler. The narrow `packages/tenancy` change does not alter Host, membership, entitlement, nominal actor or non-command route behavior.

**Nest 11 emission mechanism:** every selected committed outcome and every replay becomes an exported `CommittedCommandResponse extends HttpException` _after_ the transaction has committed (or after a durable replay lookup). It carries the persisted wire status, UTF-8 JSON bytes or an explicit no-body sentinel, and the allowlisted headers. `@TransactionalCommand` also binds an exported, method-scoped `@Catch(CommittedCommandResponse)` filter using `@UseFilters`. The filter uses Nest's `HttpAdapterHost.httpAdapter` to set the fixed JSON content type and allowed headers, then `reply(response, storedUtf8StringOrNull, storedStatus)` exactly once on the supported Express adapter. Decode persisted UTF-8 JSON bytes to a string before `reply`, after setting `application/json; charset=utf-8`; passing a Buffer would make Express JSON-encode it as an object. The no-body sentinel maps to `null`. It never returns the body to `RouterExecutionContext.createHandleResponseFn`, whose normal `apply()` path would reset POST to 201 or another route default. In Nest 11, method filters precede consumer `APP_FILTER`/global filters after `RouterExceptionFilters` reverses their combined list; filter order among stacked method decorators depends on application order, so bootstrap rejects another method- or class-level catch-all, `HttpException`-matching, or `CommittedCommandResponse`-matching filter whenever it would precede the STYNX filter in Nest’s reversed selection order. The Inspector tests both decorator orders with a consumer method-level catch-all. Ordinary outer response-mapping interceptors see an error notification, not a success value; they must not replace `CommittedCommandResponse` in `catchError`. `SlaMonitorInterceptor` must recognize this committed response as a completed HTTP response rather than a failed command. These constraints are part of the opt-in integration contract. The Inspector proves wire status/body with a consumer global catch-all exception filter and an outer response-mapping interceptor registered, including default-201 POST committed 502 and 502 replay. An unselected marker is converted to a plain `HttpException` only after rollback, so the dedicated filter cannot mistake it for committed output.

`TxOptions.requireActor?: boolean` is exported from `@stynx-nyx/data`. The boundary calls `Database.tx(..., { role: 'app', requireActor: true, retry: false })`. It owns lookup/reservation → handler → redacted audit → key completion/deletion → commit → optional cache publication, all on the same actual app-role PostgreSQL client. A 40001/40P01 surfaces after one invocation; an external delegation is never automatically retried. Failed audit, completion, statement timeout or commit rolls back domain/audit/key and publishes no cache. Replays skip handler and audit. Cache is advisory and populated only after confirmed commit; replay correctness never depends on Redis.

`Database.tx` validates `requireActor` against trusted active `RequestContext.actorId` before opening or reusing a connection, forbids owner/reader with this option, and verifies actual role/tenant/actor of a nested command transaction before SQL. This identity check applies to command/`requireActor` mode; unrelated legacy nested callers retain their savepoint contract. A nested owner-labelled Transaction on an app connection is never accepted for a command. No synthetic actor or role escalation is permitted.

## SQL ports, privileges and storage

`@stynx-nyx/contracts` adds `TransactionalAuditSink` with `writeInTransaction(event: AuditEventEnvelope, executor: AuditTransactionExecutor): Promise<void>`; the executor is a structural `query(sql, params?)` port. `@stynx-nyx/audit` adds `AuditSqlSink.writeInTransaction` using the supplied live `@stynx-nyx/data` `Transaction.query` adapter. Backend adds dependencies on `@stynx-nyx/data` and `@stynx-nyx/audit`, binding the sink through `STYNX_AUDIT_SINK`; a sink without `writeInTransaction` is rejected at boot in command mode. Legacy `AuditSink.write(event)` stays intact. `@stynx-nyx/idempotency` adds `TransactionalIdempotencyStore`, taking the supplied Transaction for every durable operation; it never opens an owner-role transaction. The unexported duplicate under `packages/backend/src/idempotency` is outside this change.

Migration `packages/data/migrations/platform/0020_transactional_commands.sql` (0019 is reserved by CTG-0004) adds response status/identity fields to `core.idempotency_keys` without rewriting legacy rows. Transactional rows carry non-null `tenant_id`; every lookup uses explicit `tenant_id = $trustedTenantId` plus mode/identity predicates. A NULL-tenant legacy row is ignored, never replayed or treated as a conflict for either tenant. Durable logical identity is **tenant + scope + supplied key**, encoded without ambiguity in the existing key column or dedicated additive fields. Method and **concrete path** belong in the fingerprint, not identity: cross-route reuse gives 409; `/requests/1` and `/requests/2` differ despite matching one Nest template. Preserve unique ownership/expiry. A concurrent identical key waits on its unique-key conflict for at most configured `lockTimeoutMs`. Immediately around **only the reservation statement**, read the current transaction-local `lock_timeout`, set the bounded value with `set_config('lock_timeout', value, true)`, execute the reservation, and restore the prior value on the success path. A reservation `55P03` aborts that PostgreSQL transaction, so roll it back before constructing the canonical 409 `IDEMPOTENCY:CONFLICT:in-progress` with `details: { key }`, `retryable:true` and no handler run; do not issue another SQL statement in that aborted transaction. A `55P03` from domain SQL or the per-tenant audit chain lock is an ordinary rollback error and never maps to `IDEMPOTENCY:CONFLICT:in-progress`. After winner commit, contender rechecks and replays/mismatches; after rollback it can acquire.

The app role currently has SELECT only on audit; existing `audit.write` is security invoker. The migration adds `audit.write_command_event(...) SECURITY DEFINER`, owned by `stynx_owner`, fixed `search_path = pg_catalog, audit`, and EXECUTE granted only to `stynx_app` and `stynx_owner` after revoking PUBLIC. It accepts no tenant or actor argument: it reads and validates nonempty UUID `app.tenant_id` and `app.actor_id` from transaction-local settings, derives `actor_role` from validated `app.role = 'app'` rather than a free-text caller argument, and forwards only those values plus bounded event fields to the existing hash-chain `audit.write`. Revoke PUBLIC access to `audit.write` without breaking owner use. The wrapper itself enforces tenant and actor validity and cannot select arbitrary tenant, actor, table or function; no audit-table INSERT/UPDATE grant is given to app. `stynx_owner` has BYPASSRLS, so `row_security = on` and FORCE RLS **do not** enforce tenant separation inside this definer function. The wrapper's checks, setting-derived tenant and `audit.write` tenant predicate carry that obligation. `app.tenant_id`/`app.actor_id` are transaction-local custom settings writable by `stynx_app`, and have the same trust boundary as current RLS, not a stronger one. Outside the function, `audit.events` and `audit.log` retain FORCE RLS and hash-chain trigger. Prove real app-role write succeeds, chain verifies, a NULL-tenant or other-tenant chain cannot be written through the wrapper despite definer BYPASSRLS, caller arguments cannot spoof identity, and rollback removes the event. The definer privilege does not relax application row visibility. Hash-chain writes serialize per tenant and may increase latency during external delegation; document this cost.

Update canonical `database/ddl`, `database/seed` if impacted, and `test/db` DDL/RLS/seed sensors with the migration. Apply from empty database and prior schema. Never hand edit generated files.

## Fingerprint, response and status policy

Fingerprint input is JSON-parsed `request.body` **before Nest pipes**, uppercase HTTP method, and the concrete `originalUrl` path with query removed, actual path parameters retained, percent escapes uppercased and trailing slash removed except `/`. Query parameters are excluded. Canonicalize JSON with recursively sorted object keys by Unicode code point and standard JSON string escaping, preserving array order. ECMAScript `JSON.stringify` normalizes numbers (`1`/`1.0` to `1`, `-0` to `0`); reject NaN, Infinity, BigInt, cycles, sparse arrays, undefined values and non-JSON objects. Body absence is determined from HTTP framing—no `Content-Length`/`Transfer-Encoding`, or zero `Content-Length`—and has its own fingerprint tag independent of Express's parsed-body placeholder (`{}` or `undefined`). Explicit JSON `null` has a distinct tag only when the consumer opts out of the default strict JSON body parser; the default parser rejects top-level `null` before this boundary. Hash a length-delimited tuple of method/path/body using SHA-256. Mismatch envelope: HTTP 409 `{ statusCode: 409, errorCode: configuredMismatchCode, message: 'Idempotency key was used for a different request', requestId: '<request UUIDv7>', details: { key: suppliedKey }, retryable: false }`; `X-Request-Id` equals the body ID. Cross-route reuse follows this rule. Scope belongs in durable identity. All new CTG5-owned rejections use the fixed canonical bodies enumerated in `errors.json`; existing `StynxDataError`, global-filter, legacy 422 and consumer-chosen bodies keep their historical wire shapes. Legacy fixed 422 `IDEMPOTENT_KEY_REUSE_DIFFERENT_BODY` remains legacy only.

The boundary serializes a selected response once before completion, stores the exact UTF-8 JSON bytes (or explicit no-body sentinel), status and allowed headers it will send, and replays those bytes/status/headers plus replay marker through `CommittedCommandResponseFilter`. The fixed content type is `application/json; charset=utf-8` when bytes exist; `content-length` is recomputed by the adapter. The replayable header allowlist is `location`, `retry-after`, `cache-control` and `etag`; never persist `set-cookie`, hop-by-hop or request-specific fields. Document this concrete allowlist in the public README. A selected `CommittedCommandError(502, { code: 'DELEGATION_FAILED', ... })` thus replays the same 502 wire status and body. A plain thrown `HttpException(502)` rolls back with no completed key. For **unselected successful** status, domain and audit commit while the reservation is deleted in the same transaction; no pending/completed key remains. An unselected error rolls back and uses Nest's ordinary error path. A status callback cannot convert an unmarked exception into a commit.
