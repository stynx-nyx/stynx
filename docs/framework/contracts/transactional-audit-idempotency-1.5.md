# Transactional audit and idempotency contract for STYNX 1.5

**Authority:** Architect. **Group:** CTG-0005 in R-0002. **Source:** DETRAN C-0002 §6.2, UPS-TXN-01…05, read only. Owner decision OD-S15-01 makes all five requirements mandatory for 1.5.0. This contract governs an opt-in mode; existing nontransactional routes keep their published behavior unless a separate contract changes it.

## One command transaction

The transactional mode has one explicit command boundary, owned by `Database.tx` on one PostgreSQL client. It begins before a marked handler executes and commits only after the handler result, selected audit event, and idempotency completion have succeeded. Each operation uses the same live `Transaction` and the same actual application connection, tenant and actor session settings. Nest interceptor order is part of this boundary: an audit write after the handler's inner `Database.tx` has committed does not qualify. An implementation may use a command transaction interceptor or an explicit command API, but the public surface must make the boundary unambiguous and usable with `@Audit` and `@Idempotent`; it must fail closed when transactional mode is requested without a live compatible command transaction. Nested service calls may use savepoints on that connection. An owner-role transaction cannot silently masquerade as an application-role transaction, and a nested role, tenant or actor mismatch must fail before SQL runs.

Commit is the publication point. A thrown command error, failed audit insert, failed idempotency completion, transaction timeout, or serialization failure rolls back domain writes, audit, and the key reservation together. A retry after rollback can claim the key. No Redis or in-memory replay entry may become visible before commit; a failed commit must not leave one. Concurrent requests for the same scoped key must have one winner and may wait for its commit, then replay or claim after rollback. Exhaustion or unavailable durable storage fails closed in transactional mode rather than executing the command without ownership.

### UPS-TXN-01 — audit

`AuditInterceptor` and `@Audit` gain an explicit transactional selection. In that selection, write the selected envelope through the active command `Transaction`, including its redaction policy and tenant/actor/request identity, before commit. The sink or adapter must be able to accept that transaction; a separate pool connection or a new `Database.tx` is not equivalent. A sink failure propagates and aborts the command. Default best-effort logging remains only for routes that did not select transactional mode. The audit write must retain the existing hash-chain and tenant RLS behavior of the selected audit storage.

### UPS-TXN-02 — idempotency

`IdempotencyInterceptor` gains an explicit transactional selection. Lookup, reservation, command execution and completion are coordinated with the command transaction on one connection. The durable reservation and completed response become visible atomically with domain and audit writes. A rolled-back command leaves neither a pending nor completed reservation. Replays never rerun the handler or append another audit event. Its existing owner-role `DatabaseIdempotencyStore` calls and Redis lock/cache path cannot be used as a substitute for same-connection transaction participation. A public-tenant route must still use the Host-selected tenant and configured nominal or verified actor from the trusted request context; a caller-supplied header or unverified token does not choose a tenant or scope.

### UPS-TXN-03 — scope, fingerprint and mismatch

Expose a route or module `scope(ctx) => string` callback, with a documented default, so a consumer may choose a subject scope or `public`. The durable key identity includes tenant, route/method, scope and supplied key; no cross-tenant or cross-scope replay is permitted. Empty or invalid scope fails before executing the handler. Fingerprint the method, normalized route and body represented as canonical JSON: object keys sorted recursively, array order retained, JSON string escaping preserved, and non-JSON or cyclic input rejected rather than ambiguously hashed. The hash is independent of object insertion order. A completed entry with the same fingerprint replays the stored HTTP status and body (and allowed response headers). A differing fingerprint returns HTTP **409** with a configurable stable code, before domain work. The current fixed 422 `IDEMPOTENT_KEY_REUSE_DIFFERENT_BODY` remains a legacy-mode behavior only unless separately migrated.

### UPS-TXN-04 — persisted status policy

Expose a status policy that decides which terminal responses are stored. The consumer can select all 2xx statuses and a deliberate 502 `DELEGATION_FAILED` terminal response. A selected status is stored with its exact body in the command transaction and replays exactly. A 502 can be persisted only when the command explicitly treats it as a terminal outcome and commits; an uncaught exception that rolls the command back cannot also leave a completed key in that same transaction. Unselected outcomes roll back or release the reservation and do not become replay entries. Document how the Nest response status/body is obtained before transaction commit, including `HttpException` handling, so persistence never depends on an after-commit interceptor.

### UPS-TXN-05 — actor requirement

`TxOptions` exposes `requireActor?: boolean`. When true, `Database.tx` validates a trusted active `RequestContext.actorId` before opening or reusing a transaction, and applies it as `app.actor_id` on the application connection. It rejects missing actor, owner/system-role execution, or a nested actor/tenant mismatch; it never supplies a synthetic actor. Existing application-role transactions already require tenant and actor in `resolveExecutionContext`; the option makes the command requirement explicit and testable without weakening that default. It must not permit owner-role escalation or RLS bypass.

## PostgreSQL and compatibility proof

Use the existing `core.idempotency_keys` and audit schema when sufficient. A schema change, if required, is additive and must update `packages/data/migrations/platform`, canonical `database/ddl`, `database/seed` where applicable, and `test/db` DDL/RLS/seed sensors together. Every new table has tenant isolation and forced RLS. Prove SQL grants and RLS under the application role, including tenant A unable to read or mutate B's key, command row or audit event. Test with real PostgreSQL and Nest HTTP, not just a mocked `Transaction`: forced rollback, audit sink failure, competing identical keys, status/body replay, canonical equivalent bodies, 409 mismatch and configurable code, scope isolation, selected 502, unselected failure, and missing/wrong actor or tenant. Preserve existing nontransactional idempotency and audit tests and API compatibility. Rebind public API baselines, trace and package release artifacts only through their authorized roles.
