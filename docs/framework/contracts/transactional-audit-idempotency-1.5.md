# Transactional audit and idempotency — STYNX 1.5

**Authority:** Architect. **Group:** CTG-0005/R-0002. **Source:** DETRAN C-0002 §6.2, UPS-TXN-01…05 (all MUST under OD-S15-01). This is an opt-in command mode. Unmarked routes retain published behavior.

## Public surface and one boundary

`@TransactionalCommand(options?: TransactionalCommandOptions)`, `StynxTransactionalCommandModule.forRoot(options: StynxTransactionalCommandModuleOptions)` and `TransactionalCommandInterceptor` are exported from `@stynx-nyx/backend`. Module options expose `auditSink: TransactionalAuditSink` and optional command defaults for `scope`, `mismatchCode`, `persistStatus` and `lockTimeoutMs`; `Database` and `TransactionalIdempotencyStore` are injected from their packages. Route options override module defaults. The module installs one global boundary with `APP_INTERCEPTOR`. A marked route also requires `@Idempotent({ transactional: true, ... })` from `@stynx-nyx/idempotency` and `@Audit({ ..., transactional: true })` from `@stynx-nyx/backend`. Existing positional `@Idempotent(headerName?, ttlMs?)` calls remain valid; the new object overload is additive. `AuditMetadata.transactional?: boolean` is additive. The boundary rejects incomplete or conflicting markings before `next.handle()`. The legacy audit/idempotency interceptors defer transactional routes to this boundary, regardless of global or method interceptor registration order. A marked route without the command module fails closed at request entry, not through a legacy interceptor. The module's Database, transactional sink and key store providers must resolve at boot; missing compatible providers fail at boot.

`TransactionalCommandOptions` contains `scope?: (ctx: TransactionalCommandContext) => string`, `mismatchCode?: string`, `persistStatus?: (outcome: TransactionalCommandOutcome) => boolean`, and `lockTimeoutMs?: number`. The context exposes trusted tenant/actor IDs, method, concrete path, request and raw parsed body. Default scope is trusted `RequestContext.actorId`, never a request header. A public route deliberately selects `scope: () => 'public'` and still supplies a configured nominal or verified actor for `requireActor`. Missing/empty scope, trusted tenant/actor or supplied key rejects before handler execution. Default mismatch code is `IDEMPOTENCY_KEY_CONFLICT`; default status policy selects 2xx; default lock timeout is 5,000 ms. Invalid callback output fails closed.

**Actor provenance at request entry:** `RequestContext.actorId` is the selected actor value, not by itself proof that a guard verified it. A protected HTTP command requires the existing guard-owned `STYNX_VERIFIED_TENANT_ID` marker, a verified principal from `StynxAuthGuard` (`stynxClaims.sub`) or `AuthContextGuard` (`principal.id`), and equality of that marker, actor and the active `RequestContext` tenant/actor. Other authentication guards have no CTG5 command provenance contract; request headers, parsed bearer claims, or a consumer-set `request.user`/`actor` field alone are insufficient. A public HTTP command must be marked `@PublicTenantRoute`; plain `@Public()` and `@System()` are not command provenance. `@stynx-nyx/contracts` adds the `STYNX_RESOLVED_PUBLIC_TENANT_CONTEXT` injection token and a read-only `ResolvedPublicTenantContextPort` with `get(request): { tenantId: string; actorId: string; mode: 'nominal' | 'verified' } | undefined`. `StynxTenancyModule` exports that provider. Its implementation stores the resolved value in a module-private `WeakMap` keyed by the request; there is no exported setter and no request property to seed. `TenantContextInterceptor` writes the map only after Host selection, active-tenant check, verified-actor membership and optional entitlement checks, and its `RequestContext` patch. For nominal mode `actorId` equals the configured UUID `publicTenant.actorId`; for verified mode the existing `STYNX_VERIFIED_PUBLIC_TENANT_PRINCIPAL` marker must be set and `actorId` equals that guard's verified principal ID. The command boundary requires a port result, the public-route metadata, and equality with active `RequestContext.tenantId`/`.actorId` before opening or reusing a command transaction. A pre-seeded request property, symbol or nonempty context alone cannot supply provenance. The port is an in-process coordination signal, not a cryptographic proof against malicious code running in the application process.

The command interceptor must execute **inside** the core/tenancy context interceptors, after their actor/tenant patch, and before the handler. Its promised independence from interceptor order applies to legacy audit/idempotency participants, not to identity establishment. `StynxTransactionalCommandModule` checks at boot that a marked public command has the exported `STYNX_RESOLVED_PUBLIC_TENANT_CONTEXT` provider and its public-tenant route metadata; existing tenancy bootstrap checks still reject missing public-tenant options. A marked protected command must have `StynxAuthGuard` or `AuthContextGuard` registered as an earlier `APP_GUARD` or on that route/class via `@UseGuards`; the module rejects an absent built-in guard at boot. Imperative `app.useGlobalGuards` registration after module initialization is not a supported provenance source for this mode. These guards clear the verified-tenant marker on entry and set it only after authentication and tenant approval, so a value pre-seeded by middleware cannot satisfy a served protected command. A wrong effective interceptor order yields no public port result and rejects before handler or SQL, rather than falling back to raw request fields. Inspector proves a valid configured order and the fail-closed wrong order. The `packages/tenancy` change is limited to this read-only provenance port; Host, membership, entitlement, nominal-actor and legacy-route behavior stay governed by the frozen tenancy contract.

`CommittedCommandError` from `@stynx-nyx/backend` is the sole committed-terminal marker: `new CommittedCommandError(statusCode, body, allowedHeaders?)`. Its status must be selected by `persistStatus`; a marker at an unselected status rolls back and surfaces through Nest's ordinary exception path with its original status/body, with no completed key or audit event. A plain thrown error, including `HttpException(502)`, always rolls back. The boundary catches a selected marker **inside** `Database.tx`, appends the selected audit event, completes the key and commits; only then does it emit the committed response. A committed terminal failure therefore has one audit event. The marker never escapes through `Database.tx` before commit.

**Nest 11 emission mechanism:** every selected committed outcome and every replay becomes an exported `CommittedCommandResponse extends HttpException` _after_ the transaction has committed (or after a durable replay lookup). It carries the persisted wire status, UTF-8 JSON bytes or an explicit no-body sentinel, and the allowlisted headers. `@TransactionalCommand` also binds an exported, method-scoped `@Catch(CommittedCommandResponse)` filter using `@UseFilters`. The filter uses Nest's `HttpAdapterHost.httpAdapter` to set the fixed JSON content type and allowed headers, then `reply(response, storedUtf8StringOrNull, storedStatus)` exactly once on the supported Express adapter. Decode persisted UTF-8 JSON bytes to a string before `reply`, after setting `application/json; charset=utf-8`; passing a Buffer would make Express JSON-encode it as an object. The no-body sentinel maps to `null`. It never returns the body to `RouterExecutionContext.createHandleResponseFn`, whose normal `apply()` path would reset POST to 201 or another route default. In Nest 11, method filters precede consumer `APP_FILTER`/global filters after `RouterExceptionFilters` reverses their combined list; filter order among stacked method decorators depends on application order, so bootstrap rejects another method- or class-level catch-all, `HttpException`-matching, or `CommittedCommandResponse`-matching filter whenever it would precede the STYNX filter in Nest’s reversed selection order. The Inspector tests both decorator orders with a consumer method-level catch-all. Ordinary outer response-mapping interceptors see an error notification, not a success value; they must not replace `CommittedCommandResponse` in `catchError`. `SlaMonitorInterceptor` must recognize this committed response as a completed HTTP response rather than a failed command. These constraints are part of the opt-in integration contract. The Inspector proves wire status/body with a consumer global catch-all exception filter and an outer response-mapping interceptor registered, including default-201 POST committed 502 and 502 replay. An unselected marker is converted to a plain `HttpException` only after rollback, so the dedicated filter cannot mistake it for committed output.

`TxOptions.requireActor?: boolean` is exported from `@stynx-nyx/data`. The boundary calls `Database.tx(..., { role: 'app', requireActor: true, retry: false })`. It owns lookup/reservation → handler → redacted audit → key completion/deletion → commit → optional cache publication, all on the same actual app-role PostgreSQL client. A 40001/40P01 surfaces after one invocation; an external delegation is never automatically retried. Failed audit, completion, statement timeout or commit rolls back domain/audit/key and publishes no cache. Replays skip handler and audit. Cache is advisory and populated only after confirmed commit; replay correctness never depends on Redis.

`Database.tx` validates `requireActor` against trusted active `RequestContext.actorId` before opening or reusing a connection, forbids owner/reader with this option, and verifies actual role/tenant/actor of a nested command transaction before SQL. This identity check applies to command/`requireActor` mode; unrelated legacy nested callers retain their savepoint contract. A nested owner-labelled Transaction on an app connection is never accepted for a command. No synthetic actor or role escalation is permitted.

## SQL ports, privileges and storage

`@stynx-nyx/contracts` adds `TransactionalAuditSink` with `writeInTransaction(event: AuditEventEnvelope, executor: AuditTransactionExecutor): Promise<void>`; the executor is a structural `query(sql, params?)` port. `@stynx-nyx/audit` adds `AuditSqlSink.writeInTransaction` using the supplied live `@stynx-nyx/data` `Transaction.query` adapter. Backend adds dependencies on `@stynx-nyx/data` and `@stynx-nyx/audit`, binding the sink through `STYNX_AUDIT_SINK`; a sink without `writeInTransaction` is rejected at boot in command mode. Legacy `AuditSink.write(event)` stays intact. `@stynx-nyx/idempotency` adds `TransactionalIdempotencyStore`, taking the supplied Transaction for every durable operation; it never opens an owner-role transaction. The unexported duplicate under `packages/backend/src/idempotency` is outside this change.

Migration `packages/data/migrations/platform/0020_transactional_commands.sql` (0019 is reserved by CTG-0004) adds response status/identity fields to `core.idempotency_keys` without rewriting legacy rows. Transactional rows carry non-null `tenant_id`; every lookup uses explicit `tenant_id = $trustedTenantId` plus mode/identity predicates. A NULL-tenant legacy row is ignored, never replayed or treated as a conflict for either tenant. Durable logical identity is **tenant + scope + supplied key**, encoded without ambiguity in the existing key column or dedicated additive fields. Method and **concrete path** belong in the fingerprint, not identity: cross-route reuse gives 409; `/requests/1` and `/requests/2` differ despite matching one Nest template. Preserve unique ownership/expiry. A concurrent identical key waits on its unique-key conflict for at most configured `lockTimeoutMs`. Immediately around **only the reservation statement**, read the current transaction-local `lock_timeout`, set the bounded value with `set_config('lock_timeout', value, true)`, execute the reservation, and restore the prior value on the success path. A reservation `55P03` aborts that PostgreSQL transaction, so roll it back before constructing the stable 409 `IDEMPOTENCY_KEY_IN_PROGRESS` with `{ key }` and no handler run; do not issue another SQL statement in that aborted transaction. A `55P03` from domain SQL or the per-tenant audit chain lock is an ordinary rollback error and never maps to `IN_PROGRESS`. After winner commit, contender rechecks and replays/mismatches; after rollback it can acquire.

The app role currently has SELECT only on audit; existing `audit.write` is security invoker. The migration adds `audit.write_command_event(...) SECURITY DEFINER`, owned by `stynx_owner`, fixed `search_path = pg_catalog, audit`, and EXECUTE granted only to `stynx_app` and `stynx_owner` after revoking PUBLIC. It accepts no tenant or actor argument: it reads and validates nonempty UUID `app.tenant_id` and `app.actor_id` from transaction-local settings, derives `actor_role` from validated `app.role = 'app'` rather than a free-text caller argument, and forwards only those values plus bounded event fields to the existing hash-chain `audit.write`. Revoke PUBLIC access to `audit.write` without breaking owner use. The wrapper itself enforces tenant and actor validity and cannot select arbitrary tenant, actor, table or function; no audit-table INSERT/UPDATE grant is given to app. `stynx_owner` has BYPASSRLS, so `row_security = on` and FORCE RLS **do not** enforce tenant separation inside this definer function. The wrapper's checks, setting-derived tenant and `audit.write` tenant predicate carry that obligation. `app.tenant_id`/`app.actor_id` are transaction-local custom settings writable by `stynx_app`, and have the same trust boundary as current RLS, not a stronger one. Outside the function, `audit.events` and `audit.log` retain FORCE RLS and hash-chain trigger. Prove real app-role write succeeds, chain verifies, a NULL-tenant or other-tenant chain cannot be written through the wrapper despite definer BYPASSRLS, caller arguments cannot spoof identity, and rollback removes the event. The definer privilege does not relax application row visibility. Hash-chain writes serialize per tenant and may increase latency during external delegation; document this cost.

Update canonical `database/ddl`, `database/seed` if impacted, and `test/db` DDL/RLS/seed sensors with the migration. Apply from empty database and prior schema. Never hand edit generated files.

## Fingerprint, response and status policy

Fingerprint input is JSON-parsed `request.body` **before Nest pipes**, uppercase HTTP method, and the concrete `originalUrl` path with query removed, actual path parameters retained, percent escapes uppercased and trailing slash removed except `/`. Query parameters are excluded. Canonicalize JSON with recursively sorted object keys by Unicode code point and standard JSON string escaping, preserving array order. ECMAScript `JSON.stringify` normalizes numbers (`1`/`1.0` to `1`, `-0` to `0`); reject NaN, Infinity, BigInt, cycles, sparse arrays, undefined values and non-JSON objects. Body absence is determined from HTTP framing—no `Content-Length`/`Transfer-Encoding`, or zero `Content-Length`—and has its own fingerprint tag independent of Express's parsed-body placeholder (`{}` or `undefined`). Explicit JSON `null` has a distinct tag only when the consumer opts out of the default strict JSON body parser; the default parser rejects top-level `null` before this boundary. Hash a length-delimited tuple of method/path/body using SHA-256. Mismatch envelope: HTTP 409 `{ code: configuredMismatchCode, context: { key: suppliedKey } }`. Cross-route reuse follows this rule. Scope belongs in durable identity. Legacy fixed 422 `IDEMPOTENT_KEY_REUSE_DIFFERENT_BODY` remains legacy only.

The boundary serializes a selected response once before completion, stores the exact UTF-8 JSON bytes (or explicit no-body sentinel), status and allowed headers it will send, and replays those bytes/status/headers plus replay marker through `CommittedCommandResponseFilter`. The fixed content type is `application/json; charset=utf-8` when bytes exist; `content-length` is recomputed by the adapter. The replayable header allowlist is `location`, `retry-after`, `cache-control` and `etag`; never persist `set-cookie`, hop-by-hop or request-specific fields. Document this concrete allowlist in the public README. A selected `CommittedCommandError(502, { code: 'DELEGATION_FAILED', ... })` thus replays the same 502 wire status and body. A plain thrown `HttpException(502)` rolls back with no completed key. For **unselected successful** status, domain and audit commit while the reservation is deleted in the same transaction; no pending/completed key remains. An unselected error rolls back and uses Nest's ordinary error path. A status callback cannot convert an unmarked exception into a commit.
