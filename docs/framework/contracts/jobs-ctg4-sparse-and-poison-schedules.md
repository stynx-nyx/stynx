# CTG-0004 supplement: sparse cron and invalid persisted schedules

**Role:** Architect. **Scope:** This supplements [Jobs 1.5](jobs-actor-timezone-1.5.md) for the two CTG-0004 delivery-review findings below. ADR-JOBS-0002, the tenant actor boundary, cron grammar, DST semantics, and the existing release gates remain authoritative. It adds the additive `ScheduleRecord.disabledReason` read property, but no new scheduling method.

## Sparse cron evaluation

`nextCronRunAt` must avoid scanning every UTC minute across long empty spans. For a syntactically valid but impossible expression such as `0 0 31 2 *`, it throws `InvalidCronExpressionError` within **500 ms per invocation in the ordinary CI Node environment**, measured around the call after module import and fixture setup. The same bound applies with `UTC`, `America/New_York`, and `America/Sao_Paulo`. The same 500 ms per-call bound applies to valid sparse expressions in `America/Sao_Paulo` and `America/New_York`: `0 0 29 2 *` after `2028-03-01T00:00:00Z` yields `2032-02-29T03:00:00Z` in São Paulo or `2032-02-29T05:00:00Z` in New York; `0 0 1 1 *` after `2029-01-02T00:00:00Z` yields `2030-01-01T03:00:00Z` or `2030-01-01T05:00:00Z` respectively. A static impossibility short-circuit is allowed only in addition to a calendar-aware skip for valid sparse schedules, never instead of it. Keep the existing five-field syntax, day-of-month/day-of-week OR semantics, canonical IANA behavior, strict-after ordering, and five-year search horizon. A calendar-aware skip or equivalent bounded candidate search may be used, but it must still inspect offset transitions around a candidate so that a fall overlap selects the later UTC occurrence and all matches in a spring gap collapse to the first valid minute. All existing New York and São Paulo fixtures remain exact.

The timing sensor uses the real implementation and full-ICU Node; it does not mock `Intl`, clocks, or the parser. It measures the function call only and records elapsed wall time. A time budget failure is a performance failure; a wrong result or DST regression is a separate correctness failure. Do not increase the 500 ms threshold to accommodate a minute-by-minute scan.

`JobsService.upsertSchedule` resolves and validates its caller context before validating timezone or evaluating the cron expression, so an unauthorized or missing caller cannot trigger the sparse computation.

## Invalid persisted schedule isolation

`stynx_app` can write directly to its own `jobs.schedules` row under FORCE RLS. SQL constraints cover column shape, not the complete cron grammar or IANA timezone validity. A malformed enabled cron row therefore cannot be allowed to abort materialization for another due row, especially another tenant's row. The owner-role `materialize(limit)` operation isolates only `instanceof InvalidCronExpressionError` raised by `nextCronRunAt` for one locked due cron schedule as follows. It does not call service `canonicalTimezone` and does not introduce a new public error class:

1. Create no `jobs.jobs` row for that invalid occurrence, and do not advance its `next_run_at` or `last_enqueued_at`.
2. Disable only that schedule and persist a stable, readable reason code, `invalid_schedule`, on its row. The reason is visible to the owning tenant through the existing schedule read path. A later valid upsert clears the reason and may re-enable the schedule under the existing actor and membership checks.
3. Continue processing the other locked due schedules in the same materialization call, including rows in another tenant. A valid row is inserted once with its persisted actor and timezone, its next run advances from its persisted `next_run_at`, and the call returns only successfully materialized rows.
4. Catch only `InvalidCronExpressionError` from `nextCronRunAt`, which covers malformed expression, timezone and impossible recurrence. `InvalidScheduleError`, unexpected SQL, connection, authorization and programming errors propagate and roll back the operation. Never use an unbounded catch to turn an infrastructure failure into a successful tick.

Persisting `invalid_schedule` requires exact column `disabled_reason text NULL` in the platform schema and `disabledReason: string | null` in `ScheduleRecord` and the schedule read projection. The column is `NULL` for healthy schedules and uses exact `CONSTRAINT schedules_disabled_reason_known CHECK (disabled_reason IS NULL OR disabled_reason = 'invalid_schedule')`. A valid authorized upsert clears the reason; `resumeSchedule` rejects an unrepaired row with existing `InvalidScheduleError` (`SCHEDULE_INVALID`); only a valid authorized upsert repairs its recurrence and clears the reason. Extend unpublished `packages/data/migrations/platform/0019_jobs_actor_timezone.sql` and `database/seed/platform/0019-jobs-actor-timezone.sql`: 0019 exists only on the unmerged CTG4 branch and no release tag contains it. Do not add a parallel migration for this branch. Preserve the existing grants, FORCE RLS policies, tenant predicates, and actorless-schedule check. Follow development-contract rule 3: update the explicit platform seed and `test/db` platform migration proof for the DDL change. No root legacy jobs DDL copy is authorized.
