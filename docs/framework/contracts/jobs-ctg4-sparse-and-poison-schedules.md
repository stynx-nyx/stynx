# CTG-0004 supplement: sparse cron and invalid persisted schedules

**Role:** Architect. **Scope:** This supplements [Jobs 1.5](jobs-actor-timezone-1.5.md) for the two CTG-0004 delivery-review findings below. ADR-JOBS-0002, the tenant actor boundary, cron grammar, DST semantics, and the existing release gates remain authoritative. It adds no new public scheduling API.

## Sparse cron evaluation

`nextCronRunAt` must avoid scanning every UTC minute across long empty spans. For a syntactically valid but impossible expression such as `0 0 31 2 *`, it throws `InvalidCronExpressionError` within **500 ms per invocation in the ordinary CI Node environment**, measured around the call after module import and fixture setup. The same bound applies with `UTC`, `America/New_York`, and `America/Sao_Paulo`. This is a bounded computation requirement, not permission to reject a valid sparse expression: `0 0 29 2 *` must find the next leap-day match, and `0 0 1 1 *` must find the next annual match. Keep the existing five-field syntax, day-of-month/day-of-week OR semantics, canonical IANA behavior, strict-after ordering, and five-year search horizon. A calendar-aware skip or equivalent bounded candidate search may be used, but it must still inspect offset transitions around a candidate so that a fall overlap selects the later UTC occurrence and all matches in a spring gap collapse to the first valid minute. All existing New York and São Paulo fixtures remain exact.

The timing sensor uses the real implementation and full-ICU Node; it does not mock `Intl`, clocks, or the parser. It measures the function call only and records elapsed wall time. A time budget failure is a performance failure; a wrong result or DST regression is a separate correctness failure. Do not increase the 500 ms threshold to accommodate a minute-by-minute scan.

`JobsService.upsertSchedule` resolves and validates its caller context before evaluating the cron expression, so an unauthorized or missing caller cannot trigger the sparse computation.

## Invalid persisted schedule isolation

`stynx_app` can write directly to its own `jobs.schedules` row under FORCE RLS. SQL constraints cover column shape, not the complete cron grammar or IANA timezone validity. A malformed enabled cron row therefore cannot be allowed to abort materialization for another due row, especially another tenant's row. The owner-role `materialize(limit)` operation must handle a **typed schedule validation failure** for one locked due schedule as follows:

1. Create no `jobs.jobs` row for that invalid occurrence, and do not advance its `next_run_at` or `last_enqueued_at`.
2. Disable only that schedule and persist a stable, readable reason code, `invalid_schedule`, on its row. The reason is visible to the owning tenant through the existing schedule read path. A later valid upsert clears the reason and may re-enable the schedule under the existing actor and membership checks.
3. Continue processing the other locked due schedules in the same materialization call, including rows in another tenant. A valid row is inserted once with its persisted actor and timezone, its next run advances from its persisted `next_run_at`, and the call returns only successfully materialized rows.
4. Catch only validation errors raised by cron expression, timezone, or a provably impossible recurrence. Unexpected SQL, connection, authorization, and programming errors propagate and roll back the operation. Never use an unbounded catch to turn an infrastructure failure into a successful tick.

Persisting `invalid_schedule` requires exact column `disabled_reason text NULL` in the platform schema and `disabledReason: string | null` in `ScheduleRecord` and the schedule read projection. The column is `NULL` for healthy schedules and constrained to `invalid_schedule` when non-NULL. A valid authorized upsert clears the reason; `resumeSchedule` rejects an unrepaired row with existing `InvalidScheduleError` (`SCHEDULE_INVALID`); only a valid authorized upsert repairs its recurrence and clears the reason. If platform migration 0019 has not been published, extend that migration. If it has been published to any consumer, add the next free forward platform migration instead of rewriting applied SQL. Preserve the existing grants, FORCE RLS policies, tenant predicates, and actorless-schedule check. Follow development-contract rule 3: update the explicit platform seed and `test/db` platform migration proof for the DDL change. No root legacy jobs DDL copy is authorized.

Because the schedule read projection is public, the Architect confirms the symbol and runs `pnpm api:baselines:write` after the Engineer change. The Architect rebinds `law/trace.json` after Inspector changes; the Engineer updates the CTG4 changeset and package READMEs through `pnpm package-readmes:write`. Run negative RLS, real integration, `pnpm ci:stynx`, and reference consumers again before the new delivery-review and PR.

The isolation proof uses real migrated PostgreSQL with two tenants and distinct owner/app role connections. Prove both direct `stynx_app` paths under tenant A's active `RequestContext`: `INSERT` of a malformed due cron schedule and `UPDATE` of an otherwise valid due schedule to a malformed expression or timezone. Prove an app-role write targeting tenant B is denied. Insert a valid due schedule for tenant B, then invoke one owner-role materialization batch covering both rows with the malformed row ordered first. Assert the malformed row is disabled with `invalid_schedule`, has no job, retains its due timestamps, and is readable by A but not B; assert B's job is materialized exactly once and its schedule advances. Repair A through the authorized service upsert and prove its reason clears. Repeat with the valid row ordered first to expose rollback of earlier successful work. A unit sensor may additionally prove that only the typed validation failure is isolated and an unexpected database error aborts. Neither an admin-pool substitute for the app proof nor `SET ROLE` inside the positive handler path satisfies the existing RLS contract.
