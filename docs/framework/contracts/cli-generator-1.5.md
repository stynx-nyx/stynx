# STYNX 1.5 module generator contract — UPS-CLI-01

**Authority:** Architect. **Status:** proposed for CTG-0008 prompt review. **Source:** DETRAN C-0002 §6.10 and OD-S15-01 (U1–U15 MUST). DETRAN's blueprint and generator are read-only precedents, not implementation sources.

## Boundary

`stynx generate module --blueprint <json> --out <directory>` is an opt-in CLI command in `@stynx-nyx/cli`. It accepts the safe **STYNX 1.5 blueprint subset** below and emits a reusable Nest module with a repository, controller, and PostgreSQL DDL with tenant RLS. It does not generate a DETRAN package, business logic, handwritten integration, RBAC grants, migrations applied to a database, or a replacement for the DETRAN local generator. The public CLI entry point is `buildProgram()` in `packages/cli/src/cli.ts`; it owns option parsing and delegates generation to separately testable internal functions. `packages/cli/src/index.ts` exports remain unchanged; Inspector tests may import internal functions by source path, while the external fixture uses only the packed CLI binary and public STYNX exports.

The blueprint is declarative data, never JavaScript, a template program, SQL fragments, or file paths. The command reads one UTF-8 JSON file. It does not fetch URLs, execute content, install dependencies, connect to a database, or mutate the input. Unknown keys and unsupported values are errors with a JSON pointer or field path, never silently ignored. This is intentionally a strict subset of DETRAN's broad schema; consumers must not assume every DETRAN blueprint is accepted. The tiny `BP-OPS-EXAMPLE-001.json` is the positive compatibility fixture. Its `auth`, `audit`, and `ops` annotations may be accepted only as metadata with the bounded shapes below; they do not create runtime authorization/audit/metrics behavior.

## Input dialect

Top level is exactly `schemaVersion`, `id`, `module`, `database`, and optional `api`, `auth`, `audit`, `ops`. `schemaVersion` is exactly `"1.0.0"`; `id` matches `^BP-[A-Z0-9]+(?:-[A-Z0-9]+)*$`. `module` requires `name`, `namespace`, `version`; permits `owners` and `description`. Names are ASCII PascalCase identifiers (`^[A-Z][A-Za-z0-9]*$`); namespace and emitted slug are lowercase ASCII identifiers of at most 48 characters (`^[a-z][a-z0-9_]*$`); the namespace is also the exact PostgreSQL schema name. Version is `MAJOR.MINOR.PATCH`. `owners` and description are inert nonempty bounded strings. A blueprint cannot specify imports, exports, handwritten members, destination names, dependency versions, arbitrary SQL, or output templates.

The **module slug** comes only from `module.name`: insert `_` before an uppercase letter preceded by a lowercase letter or digit, and between an uppercase run and its final uppercase letter when that final letter precedes a lowercase letter; then ASCII-lowercase. `Example` becomes `example` and `HTTPServer2` becomes `http_server2`. Reject a derived slug over 48 characters or a case-fold collision among declared entity names or table names. The sample's exact output names are `src/example.module.ts`, `src/example.repository.ts`, `src/example.controller.ts`, and `database/ops_example.sql`.

Reject `public`, `information_schema`, every `pg_` prefix, PostgreSQL reserved words, and every schema created by `packages/*/migrations/**/*.sql` or `database/migrations/**/*.sql`. The current pinned reserved-schema set is `archive`, `audit`, `auth`, `core`, `data`, `demo`, `flow`, `jobs`, `notifications`, `offline`, `outbox`, `sample`, `storage`, `tenancy`, and `worklist`. The repository-wide migration-check preseed at `database/migrations/000_migrate-check-preseed.sql` creates `demo` and `sample` from a literal `ARRAY`; both are reserved even when a particular fixture does not run the preseed. The packed CLI carries this pinned set because source migrations are not in its tarball. Inspector derives the union from both migration trees, recognizes that one literal preseed array as a finite list, and asserts exact equality with the validator's set; a new schema therefore fails the gate until the validator is updated. Any other dynamically constructed schema name, or a change to the preseed pattern that cannot be derived, fails the sensor for explicit review. `reference/**` migrations are excluded from this pinned platform inventory because they belong to reference applications rather than the reusable platform migration sequence; the generated DDL's existing-schema failure still protects a database where reference or adopter migrations have created the requested namespace. In particular, `offline`, `demo`, and `sample` are invalid.

`database.entities` is a nonempty array, capped at 16. Each entity has exactly `name`, `table`, `primaryKey`, `fields`, and optional `indexes`. Entity name is PascalCase; table and column names use the same lowercase identifier rule as namespace. Fields are ordered, unique, and capped at 64 per entity. Each field has `name`, `type`, and optional `nullable`, `default`. Supported types are exactly `uuid`, `text`, `varchar(N)` with `1 <= N <= 255`, `integer`, `boolean`, and `timestamptz`. Defaults are an enumerated set keyed to type: `gen_random_uuid()` for UUID, `now()` for timestamptz, boolean or integer JSON literals for those types; no user SQL string is interpolated. `primaryKey` is exactly `["id"]`. The fields must declare `id` exactly as `{"name":"id","type":"uuid","default":"gen_random_uuid()"}` and `tenant_id` exactly as `{"name":"tenant_id","type":"uuid"}`; missing fields or any additional/altered property, including `nullable` or another `default`, are errors. The generator adds `REFERENCES tenancy.tenants(id)` to the tenant column; its value comes from caller context. A generated create operation never accepts a tenant from an untrusted request body. A field without `nullable: true` is NOT NULL; primary and tenant fields cannot be nullable. `indexes` consists of distinct index objects with `columns` arrays of one to three declared column names and optional boolean `unique`. Redundant primary-key indexes are rejected. A declared nonunique single-column `tenant_id` index matches the mandatory tenant index and emits exactly one index with the deterministic mandatory name; the sample uses this case. `id` and `tenant_id` never appear in writable request DTOs. Relations, JSON schema fields, arbitrary constraints, expressions, and advanced database features are outside this version.

Optional `api` has `basePath` and `resources`. Paths are slash-delimited, lowercase literal segments with no `.`/`..`, escapes, duplicate slash, query, fragment, parameter, or trailing slash except root. A resource has `entity`, `path`, and `operations`, where `entity` names one declared entity and operations are a nonempty unique subset of `list`, `get`, `create`, `update`, `delete`. The tiny sample uses `list` and `get`. Joining `/v1` with `/example-records` produces `/v1/example-records`, never a doubled slash. Resource route collisions after normalization are errors. A missing `api` produces repository and DDL but no controller; this is a documented variation of the three-output command. `auth.rbac.roles` and `permissions` are accepted only in the sample's bounded string/operation vocabulary as inert annotations; they create no grant or role mapping. `audit.enabled` and `ops.metrics.enabled` are booleans and inert. Any unsupported metadata is rejected.

Every generated handler carries `@Permission('<namespace>.<entity-table>.<operation>')` from `@stynx-nyx/auth`, where the entity table is the exact validated `database.entities[].table` selected by that resource. This key is independent of the route path and module slug. The sample emits the literal keys `ops.example_record.list` and `ops.example_record.get`; it emits no key derived from `/example-records`. Reject a blueprint if two resources would produce the same permission key, even when their paths differ, as well as any normalized route collision. Inspector asserts those literal sample keys and uniqueness across all resource handlers. The host mounts the module behind its normal STYNX authentication and `PermissionGuard`; a principal without the exact route permission receives 403. No `@Public` decorator is emitted. The generated code does not grant permissions.

## Output and safety

`--out` is required and names a **new, absent directory** under the caller-selected workspace. The generator realpaths the caller-selected existing parent once; an ancestor symlink such as macOS `/var` is allowed. It refuses an existing final `--out` component of any kind, including a symlink, and any symlink it creates or reuses below the resolved parent. The resolved destination must stay within that parent. It creates no parent directories outside the selected existing parent and never overwrites existing bytes. Reject traversal, absolute paths in any blueprint field, Unicode confusables in emitted identifiers, path separators in identifiers, reserved SQL identifiers, case-fold collisions, duplicate tables/routes, and a resolved destination outside its selected parent. Validate the entire blueprint and plan every destination path before the first write. Stage output in a sibling temporary directory on the same filesystem, then rename atomically to `--out`; on validation or write failure, remove only its own temporary directory and leave the destination absent. The preflight absence check refuses all pre-existing files, directories, and symlinks. POSIX/Node directory rename can replace a race-created empty directory, so that concurrent race is a documented residual until a portable no-replace primitive is specified; no stronger atomic collision claim is made. Inspector probes cover the guaranteed pre-existing states. No `--force` in this CTG.

The tree is fixed: `src/<slug>.module.ts`, `src/<slug>.repository.ts`, optional `src/<slug>.controller.ts`, `src/index.ts`, `database/<namespace>_<slug>.sql`, and `generation-manifest.json`. The manifest records blueprint ID/version, SHA-256 of input bytes, generator version, and sorted relative output paths with SHA-256 digests. The generator emits a fixed header naming blueprint ID and digest in source/SQL. Inputs with identical bytes, options, and generator version produce byte-identical output, including manifest; no clock, hostname, absolute path, random identifier, locale-dependent sort, or machine-specific line endings enter output. A `--check` mode validates and regenerates in memory, compares every listed path/digest against an existing output, detects missing/extra files, and writes nothing. `--check` requires an existing ordinary directory and never treats an unparseable manifest as success. Generated files are not hand-edited. A changed blueprint requires a new absent output directory in this version; no overwrite/update mode.

The generated module/repository/controller use public STYNX package exports delivered as locally packed workspace tarballs, with no STYNX registry access. Runtime repository operations execute through `@stynx-nyx/data` `Database.tx(fn, { role: 'app' })` and `Transaction.query`, under `RequestContext` tenant/actor state. Parameter values use bound SQL parameters. Identifiers are generated only from validated names and quoted consistently. Tenant ID is sourced from trusted `RequestContext`, never a request parameter/body. Collection and item reads, writes and deletes are tenant-scoped in SQL even though RLS is the final boundary. The generated controller has typed request/response DTOs and dependency-free emitted runtime guards for the route UUID ID and each writable scalar field (type, requiredness, length/range, and rejection of undeclared properties). For create, a nonnullable field without a default is required; nullable or defaulted fields may be omitted. For update, writable fields are optional but supplied values receive the same type and bound checks. `id` and `tenant_id` are forbidden body properties for both operations, and a generated create uses the context tenant. The guards reject undeclared properties. The generator never serializes an arbitrary blueprint expression into executable code. Generated imports are limited to `@nestjs/common`, `@stynx-nyx/core` (`RequestContext`), `@stynx-nyx/data` (`Database`/`Transaction`), and `@stynx-nyx/auth` (`Permission`); the external fixture declares these packages plus their required runtime peers and `@stynx-nyx/cli`. Generated TypeScript must typecheck against those public exports and the fixture Node/Nest settings.

DDL creates exactly the `<namespace>` schema with `CREATE SCHEMA <namespace> AUTHORIZATION stynx_owner`, `REVOKE ALL ON SCHEMA <namespace> FROM PUBLIC`, and `GRANT USAGE ON SCHEMA <namespace> TO stynx_owner, stynx_app, stynx_reader`, following the platform role and grant conventions in `0018_outbox.sql`. The generated `CREATE SCHEMA` omits `IF NOT EXISTS`: an existing target namespace must fail before any generated table or grant can be applied, even if a preseed, reference migration, or adopter created it. Every emitted table, index target, and policy target is schema-qualified; generated identifiers are consistently quoted (PostgreSQL policy names themselves are unqualified on their qualified table). DDL follows STYNX platform role conventions: `stynx_owner` owns objects, `stynx_app` receives required CRUD grants, `stynx_reader` receives SELECT, and `PUBLIC` receives none. Each generated table has a non-null `tenant_id` UUID referencing `tenancy.tenants(id)` and a tenant index. It executes `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`; policy `USING` and `WITH CHECK` both compare `tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`. No `SECURITY DEFINER`, bypass-RLS role, unscoped owner transaction, or generated test-only policy. The SQL must be applicable after STYNX platform migrations in a fresh test database; it is not silently applied by the CLI. If an entity reference requires a tenant-qualified foreign key, this minimal dialect rejects it until specified in a later contract.

## Acceptance evidence

Inspector first adds failing tests for parsing, schema rejection, safe path/collision handling, atomic failure, determinism and `--check`, route joining, public API compilation, repository parameterization, and real PostgreSQL two-tenant RLS negatives including missing tenant and actor context, cross-tenant INSERT/UPDATE/DELETE, and the `INV-RBAC-001` structural route check. The structural check parses the generated controller with the TypeScript compiler API in the test-local fixture, enumerates every generated HTTP handler, and requires one nonempty exact `@Permission` key per handler, with no `@Public`, `@PublicTenantRoute`, `STYNX_PUBLIC_ROUTE` marker, or matching entry in `law/invariants/RBAC-001-allowlist.json`; it does not change `scripts/**` or rely on the repository-root route scan. Direct SQL negatives connect as `stynx_app`; catalog probes assert `relforcerowsecurity` and both `pg_policies` predicates. The tiny DETRAN sample remains the exact-compatibility fixture for `src/example.*`, `database/ops_example.sql`, `ops.example_record.list`, and `ops.example_record.get`. Inspector also applies generated DDL in a transaction after deliberately creating the target schema and asserts that it fails before creating any table or changing any grants; a pre-existing schema is never silently reused.

Inspector also authors a **STYNX-only full-CRUD blueprint** under `test/packages/cli-generator/**`. It declares all five operations and exercises every supported field type (`uuid`, `text`, bounded `varchar`, `integer`, `boolean`, `timestamptz`) and the allowed nullable and default variants. Generate it through the locally packed CLI, compile the generated source against packed public exports, and boot its Nest module in the external consumer. For each of the five routes, assert 403 without its exact permission and success with it; assert unique keys across resources. Route-level guards reject a wrong scalar type, a missing required create field, an over-length varchar, an undeclared property, and body-supplied `id` or `tenant_id`. A created row must carry the RequestContext tenant. Exercise tenant-B update and delete through the generated repository against tenant-A rows and assert zero affected rows and unchanged data, in addition to the direct-SQL RLS negatives.

The fixture recursively computes the local `@stynx-nyx/*` closure from the CLI and every other STYNX package required by the consumer, following both `dependencies` and `peerDependencies` in each package manifest; an unresolved STYNX edge fails closed. On every invocation it builds every closure member from current source in dependency order before `pnpm pack`, rather than using stale output. It maps every packed STYNX package name to its local tarball in the external consumer's `pnpm.overrides` and, before installation, asserts that the override keys exactly equal the computed closure. It pins required third-party and Nest/runtime peers to versions present in the frozen workspace dependency graph. The temporary consumer lives outside the workspace and its own `.npmrc` maps `@stynx-nyx:registry` to a verified unreachable loopback endpoint. Run `pnpm install --prefer-offline`; third-party and Nest peer packages may resolve from the normal registry on a fresh runner. Before any installed STYNX code executes, parse the consumer lockfile and prove that the installed `@stynx-nyx/*` package set equals the computed closure, every STYNX resolution is `file:` for its corresponding packed tarball, and every recorded integrity equals an independently computed SHA-512 SRI for that tarball. A STYNX registry attempt, missing override, non-tarball resolution, or integrity mismatch is a sensor failure. If installation fails, classify it as a sensor failure when the output names the loopback origin or identifies the failed fetch or resolution target itself as an `@stynx-nyx/*` package (its own metadata or tarball request), even before a lockfile exists. A STYNX name appearing only as a parent in the dependency chain does not establish a STYNX fetch failure. Send other network-shaped install failures to a separate third-party registry reachability probe; classify them as environment/unobserved only when that probe also fails; an unavailable database is likewise unobserved. Every non-PASS outcome, including unobserved, exits non-zero so neither Turbo nor `ci:stynx` can report a green integration step. The runner invokes the installed CLI binary, applies generated DDL after platform migrations in a fresh real PostgreSQL database, and starts the generated Nest module. Preserve existing CLI and database tests. Architect binds new tests to an `INV-CLI-001` invariant and trace after Inspector files exist. Engineer implements only after sensors are reviewed and red for missing behavior. The separate `test/packages/cli-generator/run-integration.mjs` process is the packed-consumer and real-DB runner; `packages/cli`'s `test:int` script invokes it, so the existing root `pnpm test:int` and `ci:stynx` lane execute it. A package-level `packages/cli/turbo.json` extends `//` and sets `tasks.test:int.cache` to `false`; each invocation must execute the DB runner and cannot replay a prior PASS. It is excluded from `test/packages/vitest.config.ts`'s `**/*.spec.ts` unit population and its auth/data stub aliases; the subprocess resolves imports only from the temporary consumer's installed tarballs. No root or reference manifest edit is required. Gates include focused CLI tests, `pnpm --filter @stynx-nyx/cli test:int`, full `pnpm test:int`, real DB RLS negative and `check:rls-smoke`, package typecheck/build/lint, `ci:stynx`, package README check, API baseline check, and a delivery review. A missing PostgreSQL service is unobserved and blocks a passing RLS claim; this lane must never report a skip or Turbo cache replay as PASS.

## Compatibility and change control

The DETRAN local generator remains the owner of its 50 existing blueprints and generated files. CTG-0008 is a STYNX feature with one fixed-group changeset and one PR. Do not copy DETRAN helper code or files. The CLI command is additive; existing `init`, `migrate`, `doctor`, `privacy`, `audit`, and `adopt` semantics remain covered. CTG-0007 must reach its approved integration checkpoint before CTG-0008 Inspector dispatch. Publication/versioning requires its separate Owner decision.
