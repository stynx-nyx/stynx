# Jobs 1.5: technical actor, tenant RLS, local cron, and clock

**Authority:** DETRAN C-0002 rev.2 §6.1 UPS-JOB-01…04 and OD-S15-01 (all MUST); INV-RBAC-001; [ADR-JOBS-0002](../../../law/adr/ADR-JOBS-0002-actor-tenant-local-clock.md). This contract refines [jobs-api.md](jobs-api.md).

## Tenant-facing API and actor assignment

Every `JobsService` tenant operation — `enqueue`, `getJob`, `cancel`, `upsertSchedule`, `getSchedule`, `pauseSchedule`, `resumeSchedule`, and `deleteSchedule` — requires an active caller `RequestContext` with `tenantId` and `actorId` and executes through `Database.tx()` on the `stynx_app` role under FORCE RLS. None uses `repository.inSystem` or constructs a context from input. Each supplied `tenantId` must equal `RequestContext.tenantId`; mismatch raises a typed `JobTenantMismatchError` before SQL. Missing context raises the existing typed context error. The tenant ID is a checked selector, never authority to switch tenants. Repositories retain tenant predicates as defense in depth.

`UpsertScheduleInput.actorId` is a required nonempty UUID, persisted as `ScheduleRecord.actorId` and `jobs.schedules.actor_id`. `createdBy` remains the human audit author. `EnqueueJobInput.actorId` is optional in the TypeScript shape for source compatibility: if omitted, `JobsService` captures the active caller `RequestContext.actorId` before any system scope. Enqueue rejects an absent actor. Both explicit actor assignments require an `auth.memberships` row for `(tenant_id, user_id)` with `is_active = true` at submission. A foreign-tenant, revoked, or inactive actor raises typed `JobActorMembershipError` before the job/schedule write. An explicit actor different from the caller additionally requires an application-provided callback `authorizeTechnicalActor({ tenantId, callerActorId, technicalActorId, permission: 'jobs.assignTechnicalActor' }): Promise<boolean>`, evaluated before the write; a missing callback or denial raises typed `JobActorAssignmentDeniedError`. Same-actor assignment requires no extra permission. Neither existence in global `auth.users` nor the FK alone establishes tenant authority. The membership query runs in the caller's tenant app transaction; the permission callback cannot substitute for membership.

`JobRecord.actorId` stays nullable for historical reads. `ScheduleRecord.timezone` stores the canonical IANA zone. `UpsertScheduleInput.timezone` defaults to `UTC`, including existing callers. Fixed intervals remain elapsed-time intervals; their timezone is stored but does not change cadence. A changed cron expression or timezone recomputes `nextRunAt` from the update instant. `nextCronRunAt(expression, after, timezone?)` retains the two-argument UTC behavior.

## Queue and handler boundary

Only schedule materialization, claim, succeed, fail, and dead-letter state transitions use owner-role SQL inside explicit `withSystemContext`. `JobsWorker.tick` claims in that scope, exits it, then passes the persisted job to `JobsRepository.executeHandler(job: JobRecord, handler: JobHandler): Promise<JobExecutionResult>`. The exported `JobExecutionResult` is exactly `{ status: 'executed' } | { status: 'not_executable'; reason: 'missing_actor' | 'inactive_actor_membership' }`. Missing tenant or actor yields `missing_actor`; inactive membership yields `inactive_actor_membership`. The repository rechecks membership immediately before invocation, returns the outcome without invoking the handler on either non-executable path, and never changes job status there. The worker invokes `JobsRepository.deadLetter(id: string, workerId: string, reason: 'missing_actor' | 'inactive_actor_membership'): Promise<void>` under system context on a non-executable outcome. That method sets `status = 'dead_letter'`, fixed `dead_letter_reason = reason`, clears the lock and schedules no retry. `fail(id, workerId, error, retryAt)` remains for ordinary handler failures only. For executable jobs `executeHandler` establishes `RequestContext` from the persisted tenant and actor without nesting or inheriting system context. Handler `Database.tx()` uses `stynx_app`, sets `app.tenant_id` and `app.actor_id`, and obeys FORCE RLS. `Database.tx({ role: 'owner' })` inside a handler fails `SystemContextRequiredError`. The handler cannot see another tenant's rows, and its writes carry the technical actor. `JobHandlerContext` still exposes job, tenant, actor, and attempt data.

If the actor is absent or its membership has become inactive, the worker does not invoke the handler. It transitions the claimed row directly to `dead_letter`, sets fixed `dead_letter_reason` values `missing_actor` or `inactive_actor_membership`, clears the lock, and schedules no retry regardless of attempts. This includes pending one-shot jobs left by pre-1.5 data. Ordinary handler failures retain bounded retry and terminal dead-letter behavior. The membership preflight and handler execution are not an authorization grant across time: handlers that perform sensitive actions must still enforce their own domain permission policy.

## Local cron and DST

Accept canonical IANA names resolved by `Intl.DateTimeFormat(...).resolvedOptions().timeZone`; persist the resolved name. Reject numeric offsets, abbreviations such as `EST`, and invalid names before SQL. Full-ICU Node and the runtime tzdata are required. Cron fields match local wall-clock minutes. At a fall transition an ambiguous minute, including wildcard-hour matches, runs only at its later UTC occurrence. If `after` lies between occurrences, the later one remains eligible. At a spring gap, all matching missing minutes from that gap collapse to one run at the first valid local minute after the gap. Deduplicate it with any normal match there. A later normal match must not preempt a shifted gap run. Return a UTC `Date` strictly after `after`; keep day-of-month/day-of-week OR semantics and monotonic subsequent runs. Test `America/New_York` 2026-03-08 and 2026-11-01, plus a historical `America/Sao_Paulo` transition, UTC compatibility, invalid zones, and timezone-change recomputation. Pin tzdata assumptions in fixtures; a host with incompatible ICU/tzdata fails visibly.

## Injectable time and polling

Export `TimerHandle` (`{ unref?(): void }`), `TimerPort` (`{ setInterval(callback: () => void, ms: number): TimerHandle; clearInterval(handle: TimerHandle): void }`), and `ClockPort` (`{ now(): number }`) from jobs `types.ts`. `WorkerOptions.timer?: TimerPort`, `WorkerOptions.clock?: ClockPort`, and `SchedulerOptions.timer?: TimerPort` use those exact names. `StynxJobsModuleOptions.authorizeTechnicalActor?: (request: { tenantId: string; callerActorId: string; technicalActorId: string; permission: 'jobs.assignTechnicalActor' }) => Promise<boolean>` is the callback location. Typed errors exported from `errors.ts` are `JobTenantMismatchError`, `JobActorMembershipError`, `JobActorAssignmentDeniedError`, and `ScheduleActorRequiredError`; missing RequestContext keeps core's existing typed context errors. Defaults wrap native timers and `Date.now`. The worker clock governs retry timestamps only. `JobsRepository.materialize` keeps PostgreSQL `clock_timestamp()` for due selection and next-run advancement; `JobsService.upsertSchedule` uses wall-clock `new Date()` for initial/recomputed `nextRunAt`. Scheduler timer tests prove registration, tick invocation, overlap, and cleanup, while database integration tests control due rows explicitly. The scheduler timer does not promise virtualized due selection. `start` is idempotent, disabled instances register nothing, `stop` clears the single registered handle, and timer callbacks never overlap ticks: a callback while one tick is in flight is skipped. `stop` prevents new ticks but lets an in-flight tick finish and record status. Deterministic timer tests drive callbacks and worker retry clock without sleeps. `computeBackoffMs` already accepts a random source; inject one for exact retry assertions (or assert bounded values when using default randomness).
