# ADR — STYNX 1.1.2 assessment closure and release-lane controls

- **Status:** Accepted
- **Date:** 2026-08-31
- **Authority:** Architect, under the Owner's STYNX 1.1.2 assessment-closure request
- **Amends:** `ADR-VERSION-LINE-0001.md`, `2026-08-24-ci-economy.md`
- **Preserves:** `2026-08-16-trusted-local-rc-evidence.md`

## Context

STYNX 1.1.1 is present for all 44 publishable packages and `latest` resolves to
`1.1.1`, but the release lane did not complete autonomously. The first publish
attempt failed because its token could not create the first package version. A
replacement publish token progressed through the ordered plan, then npm rejected
`@stynx-nyx/angular-profile@1.1.1` because the non-canonical `2.0.0` history made
implicit `latest` selection illegal. The remaining packages and release tags were
subsequently completed outside the lane. That recovered registry state does not
close the release-control defect.

The same assessment found history-coupled tests, an orphaned i18n check, ambiguous
Doctor results, optional live-RLS assertions in database-backed lanes, stale package
and adopter documentation, and drift between declared and live repository
protection. These are one patch campaign because each affects whether the next
release can be interpreted as an exact, autonomous, policy-compliant observation.

## Decisions

### D1 — v1.1.2 is an ordinary unified patch

The next release is exactly `1.1.2` for the deterministic 44-package fixed group.
It uses normal Changesets versioning. The one-time `1.1.1` rebaseline machinery is
not used. Publication remains valid only through `release.yml` with `publish:true`,
an exact full candidate SHA, the Owner-controlled repository opt-in, and all
pre-publication gates green. No manual package publication or tag push is an
accepted recovery path.

### D2 — the adjudicated registry anomaly controls the npm tag argument

The ordered publisher must read the canonical registry-anomaly policy. It adds
`--tag latest` only when the exact package and historical version are named by that
policy and the candidate remains on the approved canonical `1.x` line. Every other
package retains ordinary npm tagging behavior. An unrecognized higher version,
malformed policy, package mismatch, or candidate-line mismatch fails before the
first package starts. Fixture-based tests must prove both the exact exception and
the reject population.

### D3 — package publication and installation use separate credentials

`DEVAI_REPO_TOKEN` remains an installation/read token. Publication uses
`NPM_TOKEN`, which must be a classic personal access token for an authorized
`stynx-nyx` package publisher with at least `write:packages` (and therefore package
read access); add `repo` only when access to a private linked repository requires
it. The successful progress of release run `33386150523` demonstrates that the
replacement `NPM_TOKEN` can publish. The Owner must preserve or re-verify that
scope before v1.1.2. Repository linkage remains declared in every package
manifest; linkage is not a substitute for token authority.

### D4 — CI must be independent of the repository's historical object population

Executable tests may inspect fixtures or synthetic temporary repositories only.
They must not require a named historical commit, tree, or path from the live
checkout. Shallow clones, history compaction, and repository export must not change
their result. Historical SHAs may remain prose evidence, never executable inputs.

### D5 — all existing gates become semantically binding

- `i18n:check` compares canonical Prettier-formatted output and is part of
  `devai:lint-families`.
- Database-backed audit integration and local-RC integration execution set
  `STYNX_RLS_LIVE_REQUIRED=1`; absence of live RLS verification is failure.
- Doctor reports `ok` only after a check ran and verified its claim. Missing
  prerequisites produce `skipped`, with an explicit reason.
- Package README generation rejects dependency prose outside generated markers.
- `INV-COVERAGE-001` remains a gate. The new package endpoint families must be
  claimed by Owner-authored use cases; severity is not downgraded.

### D6 — branch and release-tag protection target state

The declarative `main` policy remains the target rather than being weakened to
today's live state:

- `enforce_admins: true` and `required_linear_history: true`;
- strict required checks;
- one approving review, dismissal of stale approvals, and code-owner review;
- conversation resolution required;
- the complete 13-context list already declared in
  `.github/branch-protection.yml`.

The five declared contexts absent from today's eight-context live list remain
required because their workflows exist and protect distinct surfaces:
`semantic-pr-title`, `migration-lint`, `reference-web-e2e`, `package-policy`, and
`dependency-audit`.

An active repository ruleset must separately cover both
`refs/tags/v*` and `refs/tags/@stynx-nyx/*@*`, block deletion and non-fast-forward
updates, and restrict creation to the release workflow's GitHub Actions identity.
No administrator bypass is a release procedure. Applying branch protection or
the tag ruleset is an Owner-controlled repository-settings action.

### D7 — workflow changes and audit drift detection

`module-demo-bookmark.yml` limits push execution to `main`, so package release
tags cannot fan out its jobs. `audit.yml` runs `pnpm verify:branch-protection`
with the existing `DEVAI_REPO_TOKEN` exposed only as `GH_TOKEN`; the token must
retain read access to repository administration/protection metadata. Drift fails
the audit. Every workflow commit receives a `FORBID-CI-WITHOUT-ADR` authorization
receipt bound to this decision.

### D8 — package visibility is explicit

All 44 packages are currently private GitHub Packages. Adopters must authenticate
to `https://npm.pkg.github.com` with package-read authority and configure the
`@stynx-nyx` scope. Public-looking package names or a public source repository do
not imply anonymous package access. Changing visibility is a separate Owner
decision and is not required for v1.1.2.

### D9 — legacy versions are deprecated only after exact Owner approval

The deprecation runbook may prepare exact commands for
`@stynx-nyx/angular-profile@2.0.0`, the 38-package `0.5.0` line, and observed
`1.0.x` versions. It must re-observe each target immediately before execution,
refuse versions outside the approved set, and preserve all immutable artifacts.
No deprecation is executed by this campaign without the Owner naming the exact
plan digest and messages.

## Verification and stop conditions

Cheap deterministic checks run before expensive gates: formatting, changed-path
lint, workflow lint, fixture-focused script tests, i18n, generated README checks,
trace/schema checks, and `git diff --check`. Then the unchanged unit, integration,
E2E, performance, release, and trusted local-RC closures run. Any threshold,
population, package roster, candidate identity, credential boundary, publication
plan, or protected-setting mismatch stops the campaign.

Acceptance requires an unassisted green `release.yml` dispatch that publishes and
verifies 44/44 packages at `1.1.2`, moves every `latest` tag to `1.1.2`, and pushes
all release tags from the workflow. A partial registry state is not completion.
