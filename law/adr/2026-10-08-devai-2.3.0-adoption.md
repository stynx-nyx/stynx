# ADR-DEVAI-ADOPTION-0013 — Adopt DEVAI 2.3.0 through `init upgrade`

**Status:** Accepted.
**Authority:** Architect, under the Owner's 2026-10-08 direction to update
STYNX to `@aarusso-nyx/devai@2.3.0`, adopt the new adopter-facing features that
supersede local governance, and publish the next version together with a
measured scorecard. Owner decisions D1–D6 are recorded below.
**Supersedes:** the package identity of `ADR-DEVAI-ADOPTION-0010`.

## Context

STYNX was bound to DEVAI 1.9.0 with constitution 1.0.2. DEVAI 2.0.0, 2.1.0,
2.2.0 and 2.3.0 were published between 2026-10-05 and 2026-10-08. No commit in
that range carries the breaking marker; the action set grows from 61 to 69, the
constitution stays at 1.0.2, and the engine floor stays at Node 24. The
package's adopter migration manifest (`law/policy/adopter-migrations.json`)
lists nine entries between the bound and the installed version:

- `MIG-2.0.0-init-upgrade`: the `init upgrade` action plans and applies the
  move from the bound `devai_version` to the installed version, in the
  canonical bind order, with a doctor post-check and an upgrade receipt. It
  replaces the hand bind sequence of `ADR-DEVAI-ADOPTION-0010` and closes
  `aarusso-nyx/devai#264`.
- `MIG-2.0.0-trusted-verifier-pin`: the trusted local-RC verifier moves from
  `@aarusso-nyx/devai@1.5.4` to `@aarusso-nyx/devai@1.9.0`
  (provenance `302161f378e54d0a2b14b743a68577f4bfc43a147a1f17568941e08e14e767a0`,
  verifier source `8b215d706a828af7361f9c6799b9cb0a30c9d00b`). A repository
  that declares `ci_economy.attested_rc` regenerates the byte-compared
  `.github/workflows/devai-local-rc-verify.yml`.
- `MIG-2.1.0-post-merge-local-state`: the tracked
  `.devai/config/post-merge-host-adapter.json` becomes a path-free
  declaration; the checkout-bound attestation lives in `<git-dir>/devai/` of
  the bound checkout. This closes `aarusso-nyx/devai#266`, the worktree-path
  trap recorded in `ADR-DEVAI-ADOPTION-0010`.
- `MIG-2.0.0-experimental-agent-execution`, `MIG-2.0.0-campaign-actions`:
  the authority policy is rematerialized for the eight new actions. Nothing
  changes without an Owner activation record.
- `MIG-2.0.0-subprocess-effects-common-dir`,
  `MIG-2.3.0-subprocess-effects-pr-list`: the subprocess effects registry
  gains the `git-common-dir` and `gh-pr-list-all` read templates.
- `MIG-2.3.0-parallel-check-scheduling`, `MIG-2.3.0-green-main-final-head`:
  opt-in capabilities; nothing changes until the repository commits
  `test-task-exclusivity.json` or sets `harness_green_main.outcomeUnit`.

Doctor at 2.0.0 also honors `docs.ia.path_overrides` in
`docs-ia.workflow-page-set` (`aarusso-nyx/devai#265`), so the advisory
`docs-governance` finding carried since 1.9.0 disappears without a local
change. The closed `test-task-descriptor.schema.json` admits the committed
`test-tasks.json` unchanged.

## Decision

STYNX pins `@aarusso-nyx/devai` exactly at `2.3.0` with this identity
(`law/policy/devai-package-identity.json` 1.3.0):

| Field             | Value                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| Registry tarball  | `https://npm.pkg.github.com/download/@aarusso-nyx/devai/2.3.0/9fdfa0ed437bda8d6834b06aa0cf3241677575a5` |
| Tarball SHA-256   | `51481cf21cbe08760e17acd637fed3eb0375f56e06888dc20505b77317a46eae`                                      |
| Source commit     | `bf9a26164934b9c1279205138480c7b68e1c26d7`                                                              |
| Source tree       | `883bb9804bcf911e180a296f98288453f976caa1`                                                              |
| Signed tag object | `fedd2a99d118431341fc9530c04f6f27784f2862` (`v2.3.0`)                                                   |

1. **D1:** the materialization is produced by
   `devai init upgrade --target . --as-role architect --write`, not by hand.
   The plan reported no retired key, no refusal, no replaced default and no
   pending obligation; the receipt `.devai/config/upgrade-receipt.json` is
   committed beside the binding receipt and lists the nine applied migration
   ids and every changed file with its digest. A second run reports `no-op`.
2. **D2:** the regenerated `.github/workflows/devai-local-rc-verify.yml`
   pins the 1.9.0 verifier. Its commit is authorized by Owner
   `FORBID-CI-WITHOUT-ADR` and `FORBID-RM-RF` receipts (the generated
   workflow resets its own runner-temporary verifier directory). The
   repository variable `DEVAI_LEDGER_VERIFIER_PROVENANCE_SHA256` moves to the
   1.9.0 provenance digest when the workflow lands on `main`.
3. **D3:** the post-merge adapter declaration is committed as generated. The
   primary checkout binds its attestation into its git directory with the
   declared `bind_command`; worktrees and CI only carry the declaration. The
   GitHub Actions adapter remains the selected host identity.
4. **D4:** `harness_green_main.outcomeUnit` is set to
   `pull-request-final-head` in the scorecard sensor inputs, so F5:T9 measures
   the pull-request gate per candidate rather than per push. The parallel
   check scheduling file `test-task-exclusivity.json` is not adopted: RC runs
   stay sequential under 2.3.0, so it would not shorten the release path.
5. **D5:** the optional adopter `authority` block stays declined, as under
   `ADR-DEVAI-ADOPTION-0010` D2. No experimental activation is recorded.
6. **D6:** the 1.5.4 version marker on `main` is never published. The DEVAI
   bump cannot be a follow-up of the exact 1.5.4 candidate
   (`ADR-DEVAI-ADOPTION-0012` admits only its enumerated lane paths), so the
   next published version is the fifth stable patch 1.5.5, governed by its own
   decision record, and it ships with the first measured scorecard.

## Consequences

- Every cached local RC result is invalidated once by the package change. The
  first `pnpm devai:rc:prepare` after this decision runs the full closure.
- Until the regenerated workflow is on `main`, a pull request carrying it is
  verified by the 1.5.4 verifier that `main` still dispatches. If that
  verifier refuses 2.3.0-produced evidence, the Owner lands the pull request
  by an administrative rebase merge, as for `ADR-DEVAI-ADOPTION-0010`, and
  the push to `main` is verified under the new workflow.
- The `.devai/config` rematerialization commit carries an Owner
  `FORBID-MUTATE-INVARIANTS` receipt; the landed commits of the rebase merge
  carry post-merge receipts in the next append-only receipts commit.
- `ADR-DEVAI-ADOPTION-0004`, `0006` and `0009`–`0012` are unchanged.
- The migration plan `docs/meta/migration/stynx-devai-1.9-adoption-plan.md`
  remains the record of the 1.9.0 sequence; the 2.3.0 sequence is the upgrade
  receipt.
