## Context

The changeset release PR merged into `main` projected the root and all 44 publishable manifests to
`1.0.0`. That projection conflicts with the Owner's exact unified `1.1.1` decision and is not a
candidate, authorization, release receipt, or registry history. It must be reconciled through the
one-time governed rebaseline; it must not be adopted merely because it is now on `main`.

At this exact baseline deterministic discovery yields 44 publishable packages and 38 mutation
targets. Authenticated registry observation yields 38 existing private packages and exactly six
approved absent names: `@stynx-nyx/jobs`, `@stynx-nyx/mobile-runtime`,
`@stynx-nyx/notifications`, `@stynx-nyx/offline-sync`, `@stynx-nyx/outbox`, and
`@stynx-nyx/worklist`. Version `1.1.1` is absent from all 44 histories. These observations must be
recomputed at each frozen candidate; the machine-readable entry snapshot is
`law/policy/release-campaign-1.1.1.json`.

## Decisions

### D1 — Exact release unit and version

The release unit is the deterministically discovered 44-package roster. The one unified candidate
is exactly `1.1.1` for the root, every publishable manifest, every internal published STYNX range,
all create-app material, changelogs, changeset state, SBOM material, drafts, tarballs, and evidence.
The mutation roster is independently discovered and is exactly 38 at this baseline. Neither count
is a permanent shortcut: discovery and policy must agree, and any drift invalidates evidence.

Only the six names above may be treated as first publications. Every other publishable package must
exist, remain private, and reconcile with authenticated registry metadata. An unexpected absence,
presence, visibility change, candidate collision, partial response, malformed response, timeout,
or unauthenticated response fails closed.

The sole history exception is `@stynx-nyx/angular-profile@2.0.0`, usable only to permit candidate
`1.1.1` through registry monotonicity. It authorizes no deletion, deprecation, manual tag action, or
version substitution. `2.0.0` remains immutable non-canonical history unless the Owner separately
authorizes a precisely named later action.

#### D1.1 — PR A intentionally carries no Changeset

PR A is the governed campaign-preparation change, not a package-version candidate. It must carry
no package Changeset, including no empty Changeset added merely to make `changeset status` green.
PR B performs the one-time unified exact `1.1.1` rebaseline for the complete live roster and
materializes the corresponding manifests, changelogs, internal ranges, changeset state, SBOM,
drafts, tarballs, and evidence together.

The PR A release-status gate must therefore recognize only the exact campaign-preparation context
bound to this policy and its declared baseline, emit an empty non-promoting status projection, and
state that version projection is deferred to PR B. The exception must fail closed for an ordinary
package change, another baseline, another target version, a changed roster, any added or deleted
Changeset, or any `ci: version packages` commit. It does not authorize omitting Changesets from
ordinary development. Engineer owns the bounded deterministic classifier; Inspector must retain a
negative sensor proving that ordinary changed packages without Changesets still fail.

### D3 — Coverage policy executes; it is not retired

The F3 decision is **execute**. The coverage policy, `INV-COVERAGE-001`, its threshold resolver,
and coverage configuration remain accepted and must not be deleted or weakened for this campaign.
Every applicable publishable workspace must expose an executable coverage command, root
orchestration must discover the live roster, and the authoritative run must emit a per-package
four-metric result. The configured thresholds remain the setpoints; an uncovered package or
unreachable threshold is a real blocking observation, not permission to lower a tier, exclude code,
suppress a package, or edit tests to move the number. Any future retirement requires a separate
Architect decision that updates the invariant, trace, readiness claims, and all consumers together.

Inspector owns coverage sensors and weakening analysis. Engineer owns package scripts,
orchestration, and CI wiring. Neither may silently change the accepted threshold semantics.

#### D3.1 — Coverage population follows executable semantics, not filenames

The shared `src/index.ts` and `src/**/index.ts` exclusions are not normative. An entry module that
contains runtime declarations, initializers, control flow, I/O, or callable implementation is part
of the coverage population even when it also exports the public API. A filename convention may not
remove executable plant from measurement. A pure barrel whose content is limited to import/export
wiring may be excluded only by a narrow, reviewable classification; the classification must fail
closed if executable behavior is later added. Likewise, `types.ts` may be excluded only while it is
limited to TypeScript-erased declarations and type-only imports or exports. Runtime enums,
constants, classes, schemas, initializers, or other emitted values in a types module are
coverage-bearing.

At this checkpoint, `packages/feature-flags/src/index.ts` and
`packages/integration-adapter/src/index.ts` contain their packages' executable implementation and
must be included. Their current `src/types.ts` files are type-only and may remain excluded. The
packages do not require a product refactor merely to make coverage non-empty. Moving behavior out
of an entry module is permissible only as an independently justified Engineer design change, and
all destination implementation modules remain in the measured population.

Engineer must remove the blanket index exclusions or replace them with an equivalently fail-closed
pure-barrel classifier, and must remove the two package-local zero-threshold overrides so the
accepted resolver supplies all four thresholds. Any narrow source exclusion must identify only a
mechanically verified non-executable module and must have a negative sensor proving that adding
runtime behavior makes it coverage-bearing. Inspector may strengthen tests against the existing
public behavior, but neither test additions nor source reorganization may reduce the measured
population, thresholds, assertions, or package roster. The authoritative 44-package run remains
blocking until every package has a non-empty four-metric population and satisfies its configured
setpoints.

### D4 — Generated README dependency truth

Consumer-facing package README dependency claims must be derived from current manifests and the
deterministically discovered workspace dependency graph, never maintained as independent prose.
The Engineer mechanism must have `--write` and non-mutating `--check` modes, stable package
ordering, canonical range rendering, and byte-stable reruns. It must cover all 44 publishable
packages and distinguish runtime dependencies, optional dependencies, peer dependencies, and
development-only relationships. Internal STYNX ranges in generated README sections must agree with
the candidate policy. Missing markers, duplicate generated sections, undocumented runtime/peer
dependencies, stale ranges, or hand-edited generated content fail the release-policy gate.

### D5 — API and trace completeness

Every publishable package must have one public API baseline discovered from its manifest exports
and built declarations. The baseline roster must exactly equal the 44-package release roster;
missing `jobs`, `notifications`, and `outbox` baselines are publication blockers. Unexpected
exports, missing export targets, declaration digest drift, or a baseline generated from an unbuilt
or different tree fails closed.

Trace verification must derive counts from tracked paths and reconcile all four populations:
tracked test paths, executable tests, fixture/support paths, and supplemental governed scripts or
config attestations. At the final PR A preparation tree, the live census is 490 tracked paths, 375
executable tests, 115 support paths, and 14 supplemental paths, totaling 504 governed items. This
supersedes the earlier 481/366/115/14 = 495 observation because Inspector strengthening added nine
executable sensors without deleting or reclassifying an existing path. All 375 executable tests
must map to active invariants with current assertion projections; all active readiness-bearing
invariants must have executable sensors. An unmapped test or assertion drift is blocking.
Hard-coded stale counts may be updated only together with a complete regenerated trace mapping;
they must never be changed merely to silence the verifier.

### D6 — RLS and sourcemap observations fail closed

RLS verification is readiness-bearing only when it connects to the migrated PostgreSQL state and
executes its cross-tenant assertions before reset, as required by CI-economy Decision 6a. Missing
database configuration, unavailable PostgreSQL, inability to authenticate, zero discovered RLS
targets, or any skipped assertion is a failure to observe and therefore blocks the lane. A
developer diagnostic may report an explicit non-promoting skip, but a release, exact-main,
local-RC, or hardening profile must request live mode and cannot convert absence into success.

Sourcemap verification is readiness-bearing only when it inspects a non-empty expected population.
Before package assembly it must inspect the complete built Angular roster; after assembly it must
inspect every expected Angular tarball and map. Zero maps, missing build outputs, missing tarballs,
missing `sourcesContent`, unresolved sources, malformed maps, or roster mismatch fails closed.

### D7 — Hardening and k6

An explicit hardening dispatch with `scenario=all` must reach and successfully execute every k6
scenario. Registry authentication and DEVAI installation are prerequisites to the observation, not
substitutes for it. A 401, missing token file, dependency failure, quiescence skip, absent result,
zero summary files, failed threshold, missing comparison baseline outside the one explicit
first-seed case, cancellation, or timeout does not establish hardening evidence. The successful
workflow must bind run ID, commit, tree, scenario set, summary artifacts, and baseline identity.

### D8 — Branch and tag protection drift

Repository policy requires exact live-state observation before PR A merge and again before release.
The required contexts declared in code must equal the active branch-protection contexts; code-owner
review and conversation resolution must operate as declared; administrator enforcement must not
allow the candidate to bypass required checks. Release tag refs require a separate matching server
rule. A declarative Terraform file, local hook, or historical observation is not live enforcement.

This ADR authorizes read-only drift verification and fail-closed reporting only. Changing branch
protection, tag rules, required contexts, review policy, or bypass actors remains a separate Owner
external-action decision. PR A must not merge through an observed bypass.

PR A may be pushed solely to obtain exact-tip check-run identities while live settings still
drift, because an unpushed commit cannot have authoritative GitHub check runs. Push does not make
the candidate merge-ready. Before merge, the repository policy record and live `main` protection
must agree, every required context must be confirmed byte-for-byte from a successful check run on
the exact PR tip, and the release-tag ruleset must be active. A later commit invalidates those
exact-tip observations. No administrator or ruleset bypass may be used to merge or release.

### D9 — Fail-closed partial-publication recovery

Multi-package publication is not atomic. Before dispatch, the governed workflow must persist the
exact ordered 44-package plan and expected candidate artifact identities. After each attempted
package it must preserve an authenticated receipt containing package, version, outcome, integrity,
shasum, timestamp, workflow run, candidate commit, and candidate tree. Receipt persistence must not
expose credentials.

On the first ambiguous or failed outcome the workflow must stop initiating new publications and
must not automatically retry. Recovery begins with a fresh authenticated census of all 44 names and
classifies each as verified published, verified absent, collision, or unknown. Unknown is blocking.
Already published immutable `1.1.1` versions are never republished, deleted, deprecated, retagged,
or replaced. Preflight must recognize the recorded partial state rather than hiding it behind the
ordinary candidate-collision error. Resuming only the exact verified-absent suffix requires a new
Owner authorization naming the same candidate commit/tree, the exact published set, the exact
remaining set, their receipts, and the recovery command. Any tree, roster, artifact, or policy drift
requires a new campaign plan; no final success claim is permitted until all 44 artifacts and normal
`latest=1.1.1` outcomes independently verify.

## Downstream authority boundaries

Inspector may add or update tests only after branching from this checkpoint. Inspector must prove
the exact policy roster, the exact six absences, one anomaly, coverage execution, README drift,
API/trace completeness, fail-closed empty/skip behavior, hardening reachability, branch-policy
drift, and partial-publication recovery. Existing tests, assertions, thresholds, mutation targets,
and security gates remain intact.

Engineer may act only after the Architect and Inspector checkpoints. Engineer owns the exact DEVAI
pin and supported binding, release tooling, README generator, coverage orchestration, API material,
trace generator implementation, workflow changes, RLS/sourcemap behavior, hardening execution, and
partial-publication implementation. Engineer may not edit Inspector sensors or Architect policy.

Neither checkpoint authorizes merge, settings changes, tag creation, release dispatch, publication,
deprecation, deletion, manual dist-tag mutation, or a branch-protection bypass. Publication requires
a later exact Owner authorization naming the merged `origin/main` commit and tree.
