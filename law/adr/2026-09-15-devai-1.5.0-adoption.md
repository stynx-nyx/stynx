# ADR-DEVAI-ADOPTION-0003 — Adopt DEVAI 1.5.0 and keep mutation as external manual hardening

**Status:** Accepted.
**Authority:** Architect, under the Owner's explicit 2026-09-15 direction to
adopt the officially published `@aarusso-nyx/devai@1.5.0`, release STYNX in the
next free minor slot, and remove mutation testing from readiness decisions.
**Supersedes:** `2026-09-04-devai-1.4.5-adoption-migration.md`.
**Amends:** `ADR-DEVAI-ADOPTION-0001`.

## Context

STYNX adopted DEVAI 1.4.5 while the previously selected 1.5.0 target was not
yet published. DEVAI 1.5.0 is now an immutable published package. Its release
contract standardizes mutation as external hardening: release policy records
`mutation: none` with disposition `not-required`, and ordinary deterministic
checks remain the release-readiness floor.

STYNX still has a valuable 38-target Stryker campaign. Removing it would discard
hardening capability and historical thresholds; keeping it in the automatic
release graph would contradict the DEVAI 1.5.0 contract and continue to add
hours to every candidate.

The local assertion-binding verifier restored by PR #266 is independent of
mutation. DEVAI 1.5.0 validates the trace schema and references but does not
recompute `assertion_count` or `assertion_digest_sha256` from the test source.
STYNX therefore retains that verifier as an ordinary functional integrity gate.

## Decision

### D1. Exact published package and supported bindings

STYNX pins `@aarusso-nyx/devai` exactly at `1.5.0`, verifies its registry,
tarball, source commit, source tree, and signed tag identities, and consumes it
only from the configured registry. Constitution 1.0.1 and the adopter policy
are materialized solely through supported `devai init bind` preview/write
operations; generated `.devai/config` and `.devai/pin` files are never edited
by hand.

### D2. Release verification profile 1.4.0

The STYNX release profile advances to schema and policy 1.4.0. It retains all
ordinary capability mappings and declares `mutation_roster: []` with no
`mutation_execution`. DEVAI preflight and certification must report mutation as
`none`/`not-required` for reason `mutation-external-hardening`; neither a
synthetic PASS nor mutation evidence may influence release eligibility.

### D3. Mutation remains optional manual hardening

`pnpm test:mutation`, its executor, all 38 Stryker configurations and targets,
and their thresholds remain intact. No mandatory CI workflow, affected profile,
local profile, release-candidate profile, release profile, or transitive task
closure may select `test:mutation`. Missing, failed, or stale mutation reports
cannot promote or block acceptance, certification, or publication.

An optional compatibility task node may remain so the manual command has a
stable descriptor. Its existence confers no readiness role and mandatory graph
reachability to it is a policy violation.

### D4. Ordinary gates remain mandatory

Formatting, lint, type integrity, generated/schema consistency, unit and
integration tests, builds, consumers, end-to-end and performance tests,
database/RLS checks, security, documentation, provenance, package boundaries,
trace assertion bindings, and exact candidate identity remain fail-closed.
This adoption neither removes nor weakens functional tests.

### D5. STYNX 1.4.0 is the release line

The complete 44-package fixed group advances from 1.3.1 to 1.4.0 through one
minor changeset. No public API, runtime, DDL, or migration change is authorized
by this adoption. Versioning, merge, tag, registry publication, GitHub Release,
and Pages remain separately authorized transitions.

## Consequences

- The expensive mutation campaign is available on demand without extending the
  acceptance critical path.
- The release DAG becomes cheaper while its deterministic correctness floor is
  unchanged.
- The 1.4.5 ADR remains immutable history but no longer describes current
  adoption authority.
- Release evidence must distinguish `not-required` from PASS and must fail
  closed if any ordinary gate is absent, stale, cancelled, or bound to another
  candidate.

## Verification obligations

Sensors must prove the exact package identity and bindings, the 44-member
1.4.0 preview, empty release mutation roster, absence of mutation execution,
non-reachability from every mandatory profile, absence from remote workflows,
preservation of the manual command and 38 configurations, and continued
blocking behavior of ordinary gates.
